# Security

## Auth

The certificate, the registered clients, the tokens, revoking and rotating are Skakel's; see "Tokens" and
"Certificates" in Skakel's [`docs/protocol.md`](https://github.com/matumi-software/skakel/blob/main/docs/protocol.md). What Koppel does with them:

- **Certificate:** Koppel makes a self-signed certificate on first start (`koppel-web`, with rcgen, as Skakel makes its own), valid for ten years. Every HTTPS port presents it, UI included, the current one at each handshake. Its SHA-256 fingerprint shows in the server's Clients section.
- **Clients:** the server admin adds a client by name and gets a client ID and secret. Skakel takes control and format characters out of the name; a name with nothing left gets 400. Koppel sets Skakel's `KeepClientSecrets`, so the secret is kept inside the encrypted `secrets.json` and the admin can copy it again later from the client's row.
- **Revoking and rotating:** both block the client at once, everywhere: its tokens, its hub connections and its USB streams. Skakel tells the client why, and Koppel's client shows that it has to pair again.
- **Tokens:** OAuth 2.0 client credentials from Skakel, 30 minutes, over HTTPS only. Koppel's `/api/remote/*` takes them. A token is a random string the server remembers, not a signed one, so there is no signing key to keep or rotate, and a server that restarts forgets its tokens (clients ask again).
- **Pairing window:** Skakel 0.3.0 takes new pairing requests only while a person has opened a window on the server's Clients page (10 minutes by default, 1 to 60). Outside it a pairing request gets 403 and spends no limit, so a stranger on the network cannot fill the server's list of requests while nobody is at it. The window is closed after every start and when the role leaves the server side.

### Rotating the certificate

It is replaced from the server's Clients section. Each action answers 202 and is
confirmed by `ServerKeysChanged`, like any other change, and each is an activity entry.

- **Certificate, in two steps,** because clients pin it: Prepare makes the next certificate and Skakel tells the linked clients its fingerprint over the remote hub. The Clients section shows who has it. Switch presents it at once; switching before every client has it is allowed, after a warning. Cancel drops it. A restart anywhere in between changes nothing, because it is all in `secrets.json`.
- **On the client:** the link saves what it learns in `connection.json`: the next fingerprint as a second trusted one (`ClientConnection.NextServerFingerprint`), and after the switch the new pinned one. Only once that is saved does the link tell the server it has it. The same credentials with the fingerprint moved on to the one it was told about is the same server (`ClientConnection.Continues`): the link and the attached devices carry on, and `attached.json` moves to the new fingerprint.
- **A client offline the whole time** never hears of the next certificate. After the switch it reports `certificateMismatch`, as for any certificate it does not know, and must be paired again or given the new fingerprint under Configuration (the stored secret carries over when the new fingerprint is the one that server announced).

### UI sign-in

The UI on port 5240 (HTTPS) needs a password. There is one admin password and no user name.

- **First run:** whoever opens the UI first sets the password, as in Home Assistant, Jellyfin and Portainer. There is no setup code. To limit who that can be, setup is open only for a window (`KOPPEL_UI_SETUP_WINDOW_MINUTES`, 10 minutes), as Portainer does: from when Koppel starts without a password, or from a reset while it runs. While it is open, `POST /api/auth/setup` takes only `{ password }` and signs that browser in. After the window it answers 403 with "Setup has timed out", and the UI says to restart Koppel. With a password set it answers 409. `GET /api/auth/state` carries `setupOpen` and `setupUntil` (when setup closes, or closed; null once there is a password), so the first-run screen asks only for the password, or explains the timeout. While no password is set the UI asks for the state every 15 seconds, so it notices the timeout, or someone else setting the password first.
  - The log says once, at Warning, that Koppel is waiting for its first password, at `https://<machine>:<KOPPEL_UI_PORT>`, and until when. Nothing in it is secret. Who set the password is logged too.
  - `KOPPEL_UI_ALLOW_FROM` applies to setup as to the rest of the UI, so a native Windows install (`local`) can only be set up from that machine.
  - Earlier builds wrote a setup code to `setup-code.txt`. Koppel deletes that file on start.
  - Setup is step 1 of the first-run wizard in the UI.
- **Password:** at least 10 characters, at most 128, and not "koppel" or "password" in any case. It is hashed with PBKDF2-SHA256, 600,000 iterations and a 16 byte salt, and kept with a security stamp in the encrypted `ui-auth.json`.
- **Cookie:** `koppel.ui`, HttpOnly, SameSite=Strict, Secure (the UI is HTTPS only), a session cookie that lasts 12 hours and slides while it is used, and never more than 7 days after the sign-in (the password change does not restart that). The security stamp, the session id and the 7 day cap are checked on every request. An API call that is not signed in gets 401, never a redirect.
- **Backoff:** login and password change lock a caller for one minute after 5 wrong tries, and double the lock on each further failure, up to one hour. A caller is one whole address, an IPv4-mapped IPv6 address counting as its IPv4 address, as in Skakel's limits. Not an IPv6 /64: every host on a network shares it, so one host could lock all of them out. A try is counted before the password is hashed and given back when it is right, so parallel guesses cannot all get in ahead of the lock. The lock applies before the password is looked at, so a right guess during it is refused too. Setup has nothing to guess, so it has no backoff; the rate limit and the hash slots hold it back. The table of callers holds at most 2048 entries.
- **Hash slots:** at most 2 password hashes run at once for the whole server (setup, login and password change). A caller who arrives while both are busy gets 429 with `Retry-After: 1` at once, and the try is not counted against it.
- **Failures in the log:** every failure goes to the log. The activity log gets one `signInFailed` entry each time a lock engages, so a burst of guesses cannot push the 500 other entries out.
- **Ending sessions:** a password change, a reset or signing out invalidates the cookies and closes the live push of the sessions that ended. Signing out also revokes the session id on the server, so a copy of the cookie is refused too. The revoked ids are written to the encrypted `ui-auth.json` beside the stamp, so they hold across a restart. Each one is kept until the session could no longer have been valid (7 days after its sign-in) and dropped on the next sign-out after that; the list holds at most 4096 ids, and past that the ones that end soonest go. The session that changed the password stays signed in. A push stream also ends when its cookie runs out. In the browser the sign-in gate (`AuthGate`) shows the login screen on any 401, and re-asks the server whether the session is still good when the push stream closes and on every reconnect retry, so a session that ended during an outage does not retry forever. Signing out cancels any auth check in flight and ignores rechecks until it finishes, and a failed sign-out says so.
- **Where the rule lives:** `requires_sign_in` and `ANONYMOUS` in `koppel-web/src/surface.rs`. Every `/api/*` route of the UI surface, the live push included, needs a session by default. Anonymous: `/api/auth/state`, `/api/auth/setup`, `/api/auth/login`, `/healthz` and the SPA files. The network surface never looks at the cookie; it keeps bearer tokens.
- **Forgot the password:** run the reset command. It clears the password, changes the stamp (so every session ends) and exits. A running service sees the change through its file watcher and opens the setup window again at once; otherwise the next start opens it. Then set a new password in the UI within the window. An unreadable `ui-auth.json` is replaced by the reset.

  ```sh
  docker compose exec koppel koppel reset-password   # or: docker compose run --rm koppel reset-password, if it is not running
  sudo koppel reset-password                        # Linux package
  ```

  ```powershell
  # elevated prompt
  & "C:\Program Files\Matumi\Koppel\Koppel.exe" reset-password
  ```

### Keeping the key outside the volume

The files are sealed with AES-256-GCM. The key can come from a file kept apart from the config and keys directories, so a backup or a copy of the volume does not carry it. The first of these that applies is used:

1. **`KOPPEL_KEY_FILE`**: the path of a file. When it is set the file must exist, otherwise Koppel stops and says so.
2. **A systemd credential** named `koppel-key`: `LoadCredential=koppel-key:/etc/koppel/key` (or `ImportCredential=`) in the unit makes `$CREDENTIALS_DIRECTORY/koppel-key`, readable by the service only and not by the other users on the machine.
3. **A Docker secret** named `koppel-key`: mounted at `/run/secrets/koppel-key`. In Compose, list it under `secrets:` for the service and under the top level `secrets:` as a `file:` or `external` secret.

The file is any secret of 32 bytes or more, up to 4096; a trailing line break is ignored. Make one with:

```sh
openssl rand -base64 32 > koppel-key
chmod 600 koppel-key
```

The AES key and a key id are derived from it with HKDF-SHA256, so the same file is the same key every time. Windows ignores all of this and keeps DPAPI (Koppel warns if `KOPPEL_KEY_FILE` is set there).

Moving an install over: set the source and start Koppel. The old `koppel-secrets.key` in the keys directory is then only read, never made again, and at start every secret file sealed with it is written again with the new key (the log says how many). Once the log says so, stop Koppel, move `koppel-secrets.key` out of the keys directory (keep a copy with your offline backup, not in the volume), and start again. Losing the key outside the volume makes the secret files unreadable, as losing the keys directory does: see "If the key is lost" in `docs/config.md`. Back the key up separately from the volume.

Rotating the key, with the key in the keys directory: stop Koppel, rename `koppel-secrets.key` to `koppel-secrets.<anything>.key`, start Koppel. It makes a new `koppel-secrets.key`, reads the renamed one, and seals every file again with the new key. When the log says so, delete the renamed file. Rotating a key from outside the volume is the same with a new key file: copy the old key file into the keys directory as `koppel-secrets.<anything>.key` (a retired key may be a Koppel key file or a plain secret like the ones above), point the source at the new one, start Koppel, and delete the copy once the log says the files were sealed again.

What this buys: a copy of the volume alone, such as a backup, a snapshot or a disk image of the data folder, no longer opens `secrets.json`, `connection.json` and `ui-auth.json`. What it does not: a copy of the machine's whole file system, or root on the running machine, still has the key.

### Guards on the web surface

- **Origin and header (UI surface):** an `Origin` that does not match the request's own scheme, host and port gets 403 on any `/api/*` call, the live push included. Behind a TLS proxy the scheme comes from `X-Forwarded-Proto`. A change (anything but GET or HEAD) also needs `X-Koppel-UI: 1`, otherwise 403. A page on another site cannot add that header without a CORS preflight, which this server never grants. The UI adds it in `api/http.ts` (`uiFetch`, used by every mutating fetch). The live push is a GET, so it needs no header, which an `EventSource` cannot send.
- **Host header:** `AllowedHosts` stays `*` and is configurable. A DNS rebinding page is stopped by HTTPS: the browser checks Koppel's certificate against the rebinding page's own host name and the request fails, and a page that tries plain HTTP is only redirected to HTTPS at its own host name, where the same check fails. The SameSite=Strict cookie and the Origin and header checks stand behind that, not the host name.
- **Security headers** on every response: `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` (only that, so it cannot break the app), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- **Rate limits:** a fixed one-minute window per caller, answering 429. A caller is one whole address, an IPv4-mapped IPv6 address counting as its IPv4 address. Skakel limits its token endpoint to 60 (`KOPPEL_RATE_TOKEN_PER_MINUTE`) and its pairing endpoints to 120 (`KOPPEL_RATE_PAIR_PER_MINUTE`), and refuses a body over 4 KiB on them with 413. It also answers 429 to a registered client's token requests after 10 wrong secrets in a minute, from any mix of addresses. Koppel limits `/api/auth/setup`, `/login` and `/password` to 30 (`KOPPEL_RATE_AUTH_PER_MINUTE`), counted the same way. Nothing else has a rate limit: `/api/remote/*`, the remote hub and the streams need a valid token. Skakel sits behind the port and role check, as Koppel's own limit does, so a token or pairing request that reached the wrong port or a client-only machine gets 404 without using up an allowance (see "Limits" in ["The roles on Skakel in Rust"](skakel.md#the-roles-on-skakel-in-rust)).
- **Remote hub:** Skakel closes a connection when its token runs out, and the link makes it again 30 seconds before that, with a fresh token. Koppel shows nothing of it: no "connecting" and no entry in the activity log.
- **Connection test:** the client's Test button gets one of a fixed set of outcomes with fixed wording, never raw exception text: `ok`, `incomplete`, `unreachable`, `certificateMismatch`, `rejectedCredentials`, `clientUnknown`, `versionMismatch` (Skakel's wording, which names both sides' protocol versions), `unexpectedAnswer` and `tooManyRequests`. They are Skakel's failure kinds, mapped in `ConnectionTestResult.From`; a revoked or rotated client reads as `clientUnknown`. `unexpectedAnswer` also covers an answer over Skakel's 64 KB cap, and `tooManyRequests` a client that had too many wrong secrets in the last minute. The detail goes to the log.
- **Dev proxy:** the Vite dev server proxies `/api` to `KOPPEL_UI_URL`, default `https://127.0.0.1:5240`, the UI port, without verifying Koppel's self-signed certificate. It sets `X-Forwarded-Proto` so the Origin check passes.

### Threat model

What the design holds against:

- A stranger on the network reaching the UI: the UI needs a password, and guessing it is slowed by the backoff. Before the first password is set, though, whoever reaches the UI first during the setup window can set it and so claim the machine. `KOPPEL_UI_ALLOW_FROM` limits who that can be: the local network by default, this machine only on a native Windows install. The window closes after 10 minutes (`KOPPEL_UI_SETUP_WINDOW_MINUTES`), so a machine left without a password does not wait for anyone who comes along; a restart opens it again. Set the password as soon as Koppel first starts, and on a network you do not trust, start it with `KOPPEL_UI_ALLOW_FROM=local` until you have. Behind Docker Desktop every caller looks like the same address, so `KOPPEL_UI_ALLOW_FROM` cannot narrow it there (see `docs/windows.md`).
- A web page in the admin's browser calling the UI: SameSite=Strict, the Origin check and the `X-Koppel-UI` header.
- A stranger reaching the network surface: it is only Skakel's info, token and pairing endpoints, which have rate limits, and the remote API, the remote hub and the USB stream, which need a token from a client registered at its current generation. The UI on the same port turns away callers outside `KOPPEL_UI_ALLOW_FROM` (the local network by default) and needs the password. Plain HTTP on the port gets only a fixed redirect, before TLS.
- A stranger sending discovery packets: a server answers only a full-size probe, never with more bytes than the probe had, and a malformed or oversized datagram is dropped without stopping the answers. A probe from port 0 or from an address that is not one host (unspecified, broadcast, multicast) gets no answer, and an answer that cannot be sent is logged at debug and does not stop the next one. A client keeps a bounded list of answers (Skakel's discovery limits), and a server it hears is trusted only through its pinned certificate and the pairing code.
- A man in the middle during pairing: Skakel derives the eight-digit code from the pinned certificate, the client's name and both nonces, with a commitment, so it gets one guess in a hundred million per request, and the server limits the requests and takes them only while a person has opened the pairing window. Only the opener of a request holds its poll token, so nobody else can collect the credentials.
- A revoked client: its sessions end and it cannot get a new token.

What it does not cover:

- The browser cannot tell Koppel's self-signed certificate from an attacker's. It warns the first time, and whoever accepts the warning on a network they do not trust can be shown an impostor that collects the password. The certificate's SHA-256 fingerprint is the one under Clients, so it can be checked in the browser's certificate details. On Windows the installer sets `KOPPEL_UI_ALLOW_FROM=local`, so the UI answers this machine only; the port itself listens on every address, because other Koppel machines use it. The Docker Desktop compose file for a Windows client publishes the port on `127.0.0.1`; the one for a Windows server publishes it on every address, as a server must.
- `KOPPEL_UI_ALLOW_FROM` and the per-caller limits on sign-in and pairing go by the caller's address as Koppel sees it; forwarded headers are not read. Behind NAT, such as port publishing that rewrites the source address, every caller arrives from one address: the local network check then lets everyone in, and one caller's wrong passwords lock out everyone else's address too.
- The gateway on 3242 is plain USB/IP with no login (see ["USB client"](usb.md#usb-client)). Whoever reaches it uses the client's access to the server. On native Windows with a loopback address only the kernel's own connections get in, and only for imports Koppel asked the driver for; elsewhere, such as a container, the port publishing is all that keeps it local.
- A registered client and the server it is paired with trust each other's USB/IP traffic: what one sends goes to the other's kernel driver (`usbip-host`, `vhci_hcd` or usbip-win2's driver) as it comes, and an attached device can be any device, a keyboard that types included. Koppel checks the bus ID and VID:PID of an import, not the traffic after it.
- **On Linux and in Docker the key sits beside the files it protects.** By default `koppel-secrets.key` is in the keys directory, and the keys and config directories are one volume (`/koppel` in the image). A backup or a copy of the volume holds the key and the ciphertext together, so the encryption then protects only a copy of the config directory on its own. Anyone who can read the keys directory can decrypt the secret files. Keep the key elsewhere to change that (see "Keeping the key outside the volume" below). On Windows the key is machine-scope DPAPI: any process on the machine can unseal the files, as with 0.1.x.
- **The key is not a passphrase.** Koppel has to start unattended after a power cut, so nothing asks for one at start. A key kept outside the volume is still a file that Koppel reads at start, and root on the machine can read that file, or the process's memory, as it can for any service.
- **Memory.** Secrets are decrypted into memory while Koppel runs: the signing key, the certificate's private key, client secrets, the UI password hash. The values Koppel owns are wiped when they are dropped (`Secret`, and the buffers holding a decrypted file). That is best effort: the JSON parser's intermediate copies, the TLS stack's keys and the AES key schedule are not wiped, nothing is locked out of swap, and a core dump holds them. Turn core dumps off on a machine that matters (`LimitCORE=0` in the service, `--ulimit core=0` in Docker).
- **Logs.** The config structs print `Secret(<redacted>)` for every secret, so a `{:?}` of one cannot leak it. A test holds that line. Koppel's own log messages do not carry secrets; a log line written by hand that formats a secret is the way one gets out, and the `Secret` type has no `Display` to make that easy.
- **The 0.1.x key ring stays.** After a 0.1.x install is converted, its Data Protection key ring (`keys/aspnet`, plain XML on Linux) is left where it was, so the install can go back to 0.1.x. Until you delete it, it can decrypt whatever 0.1.x sealed. Keep it with the backup or delete it once you are sure.
- **Client secrets can be read again.** Koppel keeps each client's secret inside the encrypted `secrets.json` so the admin can copy it again from the client's row. Anyone who can read the decrypted file can read them; see "Show-once client secrets" in `docs/decisions.md`.
- The Linux container is privileged and runs as root, and the Windows service runs as LocalSystem. A flaw in Koppel is a flaw with that reach.
