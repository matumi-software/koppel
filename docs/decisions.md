# Decisions and known limits

## Known limits

- The Linux container is privileged and runs as root. Narrowing it needs a test on a real kernel. The Windows composes also run as root, because the volume belongs to it.
- The installer, the image and the release files are not signed, and a release is built by hand from a checklist (see "To release" in [building.md](building.md)). The checks in building.md are run by hand before a pull request.
- The rollback of a failed fresh install was not exercised (see ["Tested"](usb.md#tested)).
- Printers are untried, and the arm64 image and `.deb` are untested on a Raspberry Pi.
- Webcams do not stream from a Linux server to a Windows client (#22); a Windows server through usbipd-win to a Linux client does.
- The attach deadline on its own was not exercised on real hardware; it is covered by tests with fakes.
- The UI shows `gatewayFault` on the client devices page; the gateway's live `listen` status is used only to offer the attach command.

## USB layer decisions (from the feasibility study, 2026-11-02)

- **Protocol: USB/IP**, as documented in the Linux kernel. Standard clients (`usbip attach`, usbip-win2, Docker Desktop) work against it, and we do not write our own virtual USB driver. Koppel's value sits around it: auth, discovery, UI.
- **USB traffic does not go over the push or REST.** It uses its own TCP connection; on Linux the kernel takes over the socket. The push and REST stay the control channel.
- **USB/IP has no auth or encryption.** Koppel carries it in a Skakel stream (gRPC over TLS) with a small relay on each side and only allows an import after an OAuth check. The raw USB/IP port is never exposed to the network.
- **Platforms:**
  - Linux server: the kernel's `usbip-host`, driven through sysfs. Docker image, privileged.
  - Linux client: the kernel's `vhci-hcd`, driven through sysfs. Attached devices appear on the host kernel, not only in the container.
  - Windows server: start by driving an installed usbipd-win through its CLI (not bundled). Our own libusb/UsbDk engine only if that CLI becomes a limit.
  - Windows client: the usbip-win2 driver (BSD-2-Clause) in a native install.
  - macOS client: not possible (no supported virtual host controller).
- **Licence: GPL-3.0-or-later** (0.1.0 and earlier: MIT). Code from compatible projects, such as usbipd-win (GPL-3.0), may come in with its notices; GPL-2.0-only code, such as the Linux kernel's, may not. See the rule in `CLAUDE.md`.
- **Expectations:** dongles, serial adapters, HID, storage and printers work well. Webcams and audio (isochronous) work on a good LAN but not perfectly.

## UI decisions (2026-11-12)

- **No `id:` and replay from `Last-Event-ID` on the push.** A reconnect refetches every query, a handful of small GETs on a LAN. Replay would need the server to keep a buffer of events and say when the buffer no longer reaches back, and the UI would still need the refetch for that case. Revisit only if reconnect traffic shows up as a problem.
- **No command id in the 202 answer, and no `ack` on the push.** The idea was that the answer to a change names the change and the pushed value carries it back, so the UI would not have to compare values. It would change the wire on both sides and in the contract tests, and the comparison it replaces is small, covered by tests and has one useful property: it also confirms a change made by hand in the config file or from another browser. Comparing values stays.
- **Fonts are Latin and Latin Extended, woff2 only.** Every font file is embedded in the program, and the full `@fontsource` imports pulled in every subset and a `.woff` copy of each. Instrument Sans only has those two subsets anyway. JetBrains Mono also has Cyrillic, Greek and Vietnamese; a name in one of those scripts falls back to the system font in the `--font-sans` and `--font-mono` stacks, which draws all three. The ten files are in `react-ui/src/styles/fonts.css` with the packages' own unicode ranges. If the owner wants those scripts in the mono face too, add the faces there: about 20 KB per weight and script.

- **One live region, `Announcer`, instead of one per row.** The 18 scattered `role="status"` and `aria-live` places became plain text, and everything a screen reader needs to hear goes through `useAnnounce()`. Each message is a full sentence that differs from the text on screen, so a test (and a person) can tell the two apart. The activity feed is no longer a `role="log"`: it shows the same changes the pending store announces.
- **A send button that is not off until a form is valid.** With react-aria validation the rules are checked on send and the message says what to fix; a disabled button hid that. A button is off while the link is not live and while a request is in flight.
- **The password rules are copied from the server, not asked of it.** `auth/password-rules.ts` mirrors `password.rs` (10 to 128 characters, not "koppel" or "password"). A refusal that still gets through on the password change goes under the new password if that fails the rules, else under the current password (the server gives no field name).
- **Dead design system parts removed.** `SegmentedControl` and `LinkBanner` (nothing used them), the plain `DeviceCard` (only its body is used) and their CSS, specs and previews. The status card is the one place the link shows.
- **The phone title is the page's name.** `Devices` on both device pages, where it said `Devices on lab` or `Devices on this machine`; the page heading still says which.

## Guards as routers (koppel-web, 2026-11-12)

- **One router per surface, not a table.** The UI and the network surface are two `Router`s with their own layers; the port decides which a request reaches. On one shared port a dispatcher picks by `is_network_path`, the only place that names the network surface's paths. The gRPC services are the network router's fallback beside Skakel's `/skakel` calls: Skakel's paths cannot be routes, because a route with a parameter leaves it on the request and Skakel's own router counts it among its routes' parameters (a `Path<String>` there fails with 500).
- **`Ui:AllowFrom` is outside the role gate.** It was inside, so a refused address saw 404 for a path of the role this machine lacks and 403 for the rest. With the guard a layer on the whole UI router, it is outermost and answers 403 for every UI path. The network surface's paths on the UI router stay 404 before it.
- **Paths are case sensitive, and nothing is decoded for the guards.** The routers decide what a path is, so `/API/settings` and `/api/%73ettings` are not API paths. They are the UI's page or 404, never data; they used to answer 401 for the case variant.
- **The session reader is on `/api` only.** It used to run for every UI path and could clear a cookie on a file request; the page asks `/api/auth/state` on load, which does it.
- **The sign-in rate limit counts before the session check on the password change,** as before, because the limit is a layer on the three routes outside the password route's own session requirement.
- **A request with no caller address is refused (500).** `Ui:AllowFrom` used to assume loopback for one. The systemd watchdog probe adds the loopback address to its in-process request.
- **`tower-http`** (MIT, already in the tree through tonic) for the security headers (`SetResponseHeaderLayer`), `CatchPanicLayer` (a handler that panics answers 500), `TimeoutLayer` (30 seconds on the UI router only, since gRPC calls and USB streams are long) and `RequestBodyTimeoutLayer` (10 seconds without a piece of the body, on the UI router for the same reason) and `TraceLayer` (debug level). **`tower`** is a dev dependency of koppel-web, for `ServiceExt::oneshot` in the guard tests. The headers were a hand-written middleware before; the layer is the standard form. The feature flags add `http-body-util`, `tokio` and `tracing` to tower-http's own dependencies in the lock file, all already in the tree, and no new crate.
- **Not done here:** a typed error model, versioned paths and generated types are separate issues.

## Typed states and errors in koppel-web (2026-11-12)

- **The pairing has one owner.** The client's pairing (the run, its status, what the server approved, whether a confirm is saving) is one value in a `watch` channel, changed only through `send_if_modified`, so a change to the status and to what goes with it is one step. It replaces three mutexes. The push still goes out right after each change.
- **Words are enums with the same wire words.** `PairingState`, `Outcome` (the connection test, with `message()` holding the fixed wording) and `RequestState` serialise to the strings 0.2.0 sent. A unit test lists every word.
- **The 404 check matches a status, but reads it from Skakel's sentence.** Skakel 0.3.0 keeps the HTTP status of an unexpected answer in a private error type that shows as "The server answered 404.". `answered()` is the one place that reads the number back from that sentence and the caller matches on `StatusCode`. A typed status on `skakel_client::Failure` would remove it.
- **`thiserror`** (MIT or Apache-2.0, already in the tree through koppel-usb) for `RoleError`, `RegisterError`, `StartError`, `ServerStartError` and `WebError`. Their `Display` is what the strings said before, and the source is kept for the log. `StartError::Secrets` and `StartError::SessionKey` still hold the text of the secrets store and the session key, which return strings; they become typed with those files.

## One view type, concrete roles (2026-11-12)

- **The views are koppel-usb's.** `DeviceView`, `ServerDevices`, `ClientDevices`, `ClientDeviceView` and `SystemCheck` are serialised as they are; the copies and the mapping in koppel-web are gone. The activity log's `EntityRef`, `EntityKind`, `ActivityReason` and `ActivityOutcome` are koppel-usb's too, with the reasons the web side records added to the enum, because the sink trait is koppel-usb's and a second enum meant a `match` between them. The wire words are the same.
- **No role traits.** `ServerRole`, `ClientRole`, `UsbServer` and `UsbClient` each had one implementation, and the tests run the real roles over a fake kernel rather than fakes of the traits. They are concrete types with `async fn`, so there is no boxed future. A second implementation brings a trait back.
- **`Platform` and `Capabilities`.** `UsbHost::capabilities()` returns what the host can do (share, unshare, reset, and its kind) as one value, in place of four methods. `Platform { host, attacher, driver, native_windows }` is what `koppel` builds from the settings and `koppel-web` and the client are given; `Unsupported`, which implemented three traits, is gone. A missing attacher or driver is `None`, and the platform answers "why" with one reason. `share_check` and `attach_check` take the platform, so the "native Windows" flag is a field.
- **Attach and detach do not block a worker.** The vhci write to sysfs runs on `spawn_blocking` (`Platform::attach_kernel` and `detach_kernel`). The socket is handed over as a duplicate, which the kernel holds on to as it did the original.
- **`test-util` feature.** `stream::memory` and the types a test double needs (`UsbDevice`, `UsbError`, `VhciPort` and the rest) are public only with it; the crate's own tests and koppel-web's turn it on as a dev-dependency. The crate root now exports what koppel and koppel-web use. A crate that depends on itself for a dev feature is how Cargo spells this, and it adds a `koppel-usb` line to koppel-usb's entry in `Cargo.lock`.

## koppel-usb 0.2.1 decisions

- **States and ids are types.** `DeviceState`, `LinkState` and `EntityKind` serialise to the same words as before (`local`, `shared`, `attached`, `offline`; `unconfigured`, `connecting`, `connected`, `error`; `device`, `link`), so nothing on the wire or in the UI changes. A state word this version does not know reads as `local`. `BusId` can only be made from a valid bus ID, and reading a device list leaves out a row whose bus ID is not one instead of failing the whole list. `UsbError` is a `thiserror` enum whose `Display` is the sentence the UI shows and whose I/O source stays for the log.
- **Left for the web side.** The pairing and link string states in koppel-web (`PairingState`, `roles/skakel/client.rs`), the 404 match, `RoleError` and `StartError` are koppel-web's and were not touched. `LinkStatus::Down(String)` and `OpenError::{Refused, Failed}(String)` keep their strings: the transport (koppel-web) makes them from Skakel's fixed wording.
- **One actor per role.** `UsbClient` and `UsbServer` each have one task that owns the state and takes every change as a command. Each device on the client is a slot in a state machine with no I/O (`client/slots.rs`), keyed by the connection epoch, tested against a model with `proptest-state-machine`. The snapshot pump and `Handlers<T>` became `tokio::sync::watch`: a listener is one task per listener, not one per event, and sees the newest value.
- **The machine is named `SlotState`, not `DeviceState`,** because the UI's state word already has that name.
- **Dependencies.** `thiserror` (MIT OR Apache-2.0, already in the tree). `http` (MIT OR Apache-2.0, already in the tree through axum and hyper) reads a URL's authority and `Usb:Upstream`, in place of hand-written splitting. Dev only: `proptest` and `proptest-state-machine` (MIT OR Apache-2.0) with tokio's `test-util`. `cargo deny check` passes with the existing licence list.
- **`same_fingerprint` stays hand-written.** It compares two fingerprints on their hex digits only; no crate does exactly that, and the code is eight lines with a test.
- **`relay` is not swapped for `tokio::io::copy_bidirectional`.** The stream to the other machine frames its writes, and `relay` writes each read as one write and flushes it, one message per read, as 0.1.x did (pinned by `one_read_is_one_write_and_one_flush`). `copy_bidirectional` reads into 8 KiB and flushes only when the reader would block, which changes the frames. Whether that matters on a Skakel stream under real USB traffic needs a real device, so the swap waits for one.
- **`loopback_pair` is not swapped for a `socketpair`.** It would save a listener and a port per attach on Linux, but the pair is handed to the kernel (`vhci-hcd`, `usbip-host`), and only a real kernel proves that a socketpair works there.
- **Monotonic time.** Retry throttling, the upstream refresh and the poll back-off read `Clock::monotonic` (tokio's `Instant`), so a step of the wall clock cannot stall them. The wall clock stays for what people read.

## koppel-windows 0.2.1 decisions

- **The tray pipe is written from a thread per tray.** `TrayProcess::send` puts the line on a bounded channel (32 lines) and returns; a thread owns the write end of the pipe. A tray that does not read fills its queue and further lines are dropped, with a debug line, instead of blocking the launcher. A state is sent again on the next round, so nothing is lost that matters. Closing the pipe drops the sender, so the thread ends and the pipe closes after the queued lines.
- **The tray's lines are a tagged enum.** `wire::Line` has `State`, `Notice` and an `Unknown` variant (`#[serde(other)]`), so a newer service can add a type. A known type with a field of the wrong kind (a number for `tip`) is now skipped as a whole line, where a non-boolean `attention` used to read as false. `wire` builds on every platform, so its tests run in the Linux container.
- **Tray state lives behind `GWLP_USERDATA`.** The statics are gone. The window owns a `Tray` that `WM_NCDESTROY` frees. Windows does not say which notification was clicked, so the page of a click is the page of the newest notice, cleared when that notice times out or is hidden. A click on an older one from the Action Center opens the UI's start, not another notice's page.
- **`winreg` for the `UiUrl` value** (MIT, on windows-sys, already in the tree), in place of raw Registry calls. The `windows` Registry feature stays on because the bindings gate `ShellExecuteExW` behind it.
- **The health probe does not pin the certificate.** It sends nothing and only learns that something answers 200 on the UI's address; the browser that the Start menu entry opens afterwards checks the certificate itself. Pinning would need the fingerprint in a place every user can read and kept in step with renewal. The reasoning is in `health.rs`.
- **Unsafe is denied in `koppel-windows` except in the modules that call the Windows API** (`event_log`, `health`, `launcher`, `opener`, `shell`, `tray`). `service`, `ui_url` and `wire` have none.
- **The UI address passed to a tray is quoted**, and `ui_url::checked` refuses an address with a quote in it.

## Settings and commands (2026-11-12)

- **clap for the command line and the settings.** Picked over argh, lexopt and pico-args because it is the standard, takes the environment variable as an attribute of the option (`env`), prints the help and the `--version` line, and refuses an unknown option, which is the whole point of the change. clap 4.6.7 (MIT OR Apache-2.0, already in `deny.toml` and `about.toml`), with default features off and `std`, `derive`, `env`, `help`, `usage` and `error-context` on. What it costs, measured on a Windows release build with the project's size profile: `Koppel.exe` 7,529,472 bytes before, 7,824,896 after the settings change as a whole (clap and the healthcheck together, with the healthcheck still on hyper), so about 295 KB, 3.9 percent. That is the price of a real parser and `--help` on a size-tuned binary; lexopt would be a few KB but would leave the help, the environment and the validation to hand-written code.
- **Names.** `KOPPEL_` and the option in capitals (`KOPPEL_UI_PORT`), flat, not `KOPPEL_PORTS_UI`: the section half of 0.1.x's names only mirrored .NET's configuration tree. 0.1.x's names are aliases that log once as deprecated and are kept through 0.2.1; dropping them is the owner's call for a later release. The aliases are rewritten to the new options before clap reads anything, so there is one parser and one set of rules, and a test checks that every variable in the struct has an old name and every old name has an option.
- **`healthcheck` is a TLS handshake and one fixed request, not an HTTP client.** Measured on the same build: the hyper client version was 7,824,896 bytes, the raw version 7,795,712, so 29,184 bytes (0.4 percent) less, and `koppel` no longer asks for hyper's `client` feature or the `hyper-util` and `http-body-util` crates. The code is shorter too: it sends `GET /healthz HTTP/1.1` with `Connection: close` and reads only as far as the status line. The certificate check is still off, for the same reason as before (see `healthcheck.rs`). The saving is small; what decided it is that an HTTP client was more machinery than a status line needs.
- **Blank is unset.** A blank value (`KOPPEL_UI_PORT=` from a compose file's `${VAR:-}`) leaves the setting at its default, as a blank value did in 0.1.x.


## Secrets at rest decisions (2026-11-12)

- **A key outside the volume, not a passphrase.** Koppel starts unattended, so nothing can ask for a passphrase. `KOPPEL_KEY_FILE`, a systemd credential and a Docker secret keep the key apart from the volume, which is what a backup copies. All three are a file; one code path reads them. They are tried in that order, and a `KOPPEL_KEY_FILE` that names nothing stops start-up instead of quietly falling back to a key beside the files.
- **The key file is any secret, derived with HKDF.** An admin makes it with `openssl rand -base64 32` rather than a Koppel tool. HKDF-SHA256 (ring, already a dependency) turns it into the AES key and the key id, so the id stays stable and says which files the key opened. Considered: requiring Koppel's own `KPSK` format. That would need a command to make one for a Docker secret or a credential, for no gain.
- **A key ring of every readable key, sealing with one.** The container already carried a key id and refused any other, so a rotation was a dead end. The ring is cheap: the keys directory's `koppel-secrets.key`, any `koppel-secrets.<anything>.key` (older keys) and the outside key. The sealing key is the outside key when there is one, otherwise `koppel-secrets.key`. "Newest by file time" was rejected as fragile; the name decides. Files sealed with another key are written again at start, so a rotation or a move is one restart.
- **Password hash stays PBKDF2-SHA256 through ring.** 600,000 iterations is the OWASP figure for PBKDF2-HMAC-SHA256. Argon2id would be better against GPUs, but it needs a new dependency (the RustCrypto `argon2` crate), a second hash format next to the 0.1.x one that carried over from existing installs (so a login would verify two formats and rehash), and the hash only protects a password that is already behind a rate limit, a lock-out and a 128 character cap, inside a file that is encrypted. The gain is small and the migration is not. Revisit if the hash ever leaves the encrypted file.
- **Client secrets stay retrievable (`KeepClientSecrets`).** Showing a secret once and keeping only its hash would stop an admin copying it again from the client's row, which they do. The gain is small: the token signing key sits in the same encrypted file and lets whoever reads it forge a token for any client, so a reader of the file does not need the client secrets. It would also change the UI. If that file's confidentiality is ever split (the certificate's private key kept elsewhere), show-once becomes worth it. Revisited with Skakel 0.3.0, whose tokens are random strings the server remembers: there is no signing key in the file any more, so the sentence above about forging tokens no longer holds, and what a reader of the file gets is the certificate's private key and the client secrets. The decision stands, since show-once would still change the UI for a small gain.
- **`Secret<T>` over a hand-written `Debug` per struct.** A newtype cannot be forgotten on a new field the way an impl can, and it carries the wipe on drop. Cost: `.as_deref()` on an optional secret gives `&String`, and code that builds the structs needs `.into()`.
- **No proptest, no cargo-fuzz.** The properties (seal then open is the identity, a flipped byte or a truncation is an error and never a panic, the PKCS#12 reader never panics on random or damaged DER) run as ordinary tests on a fixed xorshift generator, thousands of cases in about a second. proptest would add a dev dependency tree and shrinking, which short byte inputs do not need. A cargo-fuzz harness needs nightly and a separate crate; add one if the PKCS#12 reader is ever opened to input from outside a file the admin carried over.
- **The 0.1.x key ring is not deleted after conversion.** Deleting it would stop a rollback to 0.1.x, and the code that converts is being moved out of the daemon (issue #144). It is documented in the threat model instead.

## The upgrade leaves the daemon (2026-11-12, #144)

- **`koppel-upgrade` is a crate of its own, called by `koppel` at every start.** The Data Protection reader, the PKCS#12 reader, the conversion and the rewrite of `secrets.json`, with their tests and fixtures, live there. `koppel-config` lost `aes`, `cbc`, `des` and `roxmltree` and reads only the current shape. `koppel` still links them, so a 0.1.x or 0.2.0 install converts with no step from the owner. Against the case for a separate command: a command someone must remember is how an upgrade leaves a daemon that cannot start.
- **The certificate is stored as `{ certificate, privateKey }`, DER and PKCS#8 in base64,** which is Skakel's own `CertificateRecord`. The PKCS#12 writer is gone from the build (the tests keep one to make input). The DER is unchanged, so fingerprints are.
- **`ServerSecrets` holds `skakel_server::SkakelState` itself.** koppel-config depends on skakel-server (already in the tree) and the field-by-field mirror in `store.rs` is gone. Cost: client secrets and the key are plain `String`s inside Skakel's type, not `Secret<String>`. Skakel's `Debug` hides them, and it is the type that owns them.
- **Plain serde in place of the .NET emulation.** `serde_json::to_vec_pretty`, `time::serde::rfc3339`, `indexmap::IndexMap` (MIT OR Apache-2.0, already in the tree). Reading stays lenient for a byte order mark, `Z` or `+00:00`, `null` lists and the 0.1.x computed names; `settings.json` takes capitalised names and roles through `#[serde(alias)]`. Dropped: names in any case on nested and API fields, and `"server, client"` reading as `client`. Written dates are now `Z` with up to nine digits, not `+00:00` with seven; the contract test and the UI accept both.
- **The 0.1.x key ring is kept by default, and there is no command to remove it.** Case against: its master key sits in plain base64 on Linux, and an upgrade that leaves it is a secret at rest nobody uses. Case for: deleting is irreversible and ends a rollback, and the owner may not have a backup yet. What would change it: a report of a key ring read from a backup. It stays, the log says so once at the conversion, and `docs/config.md` says how to remove it by hand.
- **Not done: the two parallel maps in `devices.json` and `attached.json`** (`busIds` and `vidPids`). They are the on-disk shape 0.1.x and the contract tests use; merging them is a format change of its own.

## Upgrades, logs and the service (0.2.1)

- **The `.deb` upgrades like a debhelper package.** First install enables and starts the unit. An upgrade keeps a disabled unit disabled (checked with `systemctl is-enabled`, because 0.2.0 enabled the unit without the helper's record) and uses `try-restart`, so a stopped service stays stopped and a running one picks up the new version. A restart still drops shared devices and attached links for a moment; that is the price of running the new binary, and it only happens to a service that was running. The scripts are tested in a Debian container against `deb-systemd-helper` and `deb-systemd-invoke`.
- **A changelog and a man page are checked-in files** (`changelog` in Debian format, `koppel.1` in roff), gzipped in the Dockerfile. The settings work (#145) put clap in, so the page could be generated with `clap_mangen`, but that is a new dependency and a build step in the Dockerfile; the page lists the commands and the main settings by hand instead, `koppel --help` has the full list, and the release checklist says to update the page with the command line. Generating it is a follow-up.
- **The Windows log file is size-capped by Koppel's own writer.** `tracing-appender` rotates by time only (and keeps N files, not N bytes), so it supplies the non-blocking thread and `SizeRotatingFile` does the rotation: 5 MiB, five files. A rotation that fails because a reader holds the file keeps writing to the current one. `tracing-appender` is MIT and from the tokio project, as `tracing` is.
- **`koppel diagnostics` is one text file, not a zip.** A zip crate would be a new dependency for a report a person reads and attaches; sections in one file do the same job. The logic is `koppel_config::diagnostics`; `koppel/src/diagnostics.rs` and three lines in `main.rs` only wire it. Secrets are removed by name (`password`, `secret`, `token`, `key`, `credential`, `passphrase`, `hash`, `stamp`) at any depth, so a field added later is covered; the encrypted files and the keys folder are never read.
- **The service gets an unrestricted SID.** `sc sidtype Koppel unrestricted` only adds `NT SERVICE\Koppel` to the token. `restricted` would add a second access check against that SID and lock the service out of `%ProgramData%\Koppel` until every ACL names it.
- **The service keeps eight privileges.** The installer runs `sc privs Koppel` (the `SetServicePrivileges` action in `Package.wxs`, after `SetServiceSid`) so the service token holds only these, and not the thirty or so LocalSystem starts with. WiX 5.0.2's `util:ServiceConfig` has no attribute for it (the extension's binary holds no string with `Privilege` in it, read by searching it), so it is `sc.exe` through `WixQuietExec`, as the SID is. `Return="ignore"`: if `sc` fails the service keeps what it has always had and the MSI log says why. The list takes effect at the next start of the service, which is after the action. Each line below says whether it was read from the code, from the vendored binaries, or taken from Microsoft's documentation of the API; which privileges a LocalSystem token holds and how an API checks them is the second kind, because the agent that wrote this could not run elevated or install anything.
  - **`SeTcbPrivilege`: kept.** `WTSQueryUserToken` (`koppel-windows/src/launcher.rs`) needs it. Documented by Microsoft.
  - **`SeAssignPrimaryTokenPrivilege` and `SeIncreaseQuotaPrivilege`: kept.** `CreateProcessAsUserW` with the session user's token (`launcher.rs`) needs both. Documented by Microsoft.
  - **`SeChangeNotifyPrivilege`: kept.** Bypass traverse checking: every path the service opens (config, keys, logs, `usbip.exe` under Program Files) is reached through folders it may have no list right on. Every service token has it and losing it breaks file access in ways that show up late.
  - **`SeImpersonatePrivilege`: kept, unsure.** Read from the code: nothing impersonates (no `Impersonate*` call, no named pipe or RPC server; the tray's pipe is anonymous and made with `CreatePipe`). What the Windows components the service calls (DPAPI through lsass, the Event Log) ask of the caller was not measured. Test that would remove it: install, drop it from the list by hand, restart the service, and check that the service starts, the secret files open (the UI signs in), the event log gets entries and the tray comes up.
  - **`SeCreateGlobalPrivilege`: kept, unsure.** Read from the code: Koppel creates no named kernel object, so it should not be needed. The runtime and the libraries under it were not checked for one. Same test as `SeImpersonatePrivilege`.
  - **`SeRestorePrivilege` and `SeTakeOwnershipPrivilege`: kept, unsure.** At every start the service sets the owner of `%ProgramData%\Koppel`, its `config` and `keys` folders and the log folder to Administrators and replaces their ACLs (`harden_directory`). Giving ownership to a group the caller is not needs `SeRestorePrivilege` unless the group is in the token with the owner flag, which Microsoft's documentation says a LocalSystem token has and which was not seen here. Replacing the ACL of a folder that gives SYSTEM no `WRITE_DAC` (an administrator's own `Paths:Config` folder is the case) needs `SeTakeOwnershipPrivilege`. Test that would remove them: with them dropped, start the service with `Paths:Config` and `Paths:Keys` pointing at new folders on another drive, one of them with SYSTEM taken off its ACL, and see whether the start succeeds. If it does, both go.
  - **Dropped, with the reason:** `SeDebugPrivilege` (no process is opened except ones the service started, whose handles come from `CreateProcess`), `SeBackupPrivilege` (nothing opens a file with backup semantics, and `sync_directory` is a no-op on Windows), `SeSecurityPrivilege` (the SACL is never read or written: only the owner and the DACL are set), `SeAuditPrivilege` (the event log is the Application log through `ReportEventW`, not the Security log), `SeLoadDriverPrivilege` (the service loads no driver: the driver goes in during setup through `driver.ps1` as the installer's SYSTEM, and `usbip.exe` and `libusbip.dll` 0.9.8.1 import `CM_Get_Device_Interface_List`, `CreateFileW` and `DeviceIoControl` and no `SetupDi*`, `AdjustTokenPrivileges` or privilege name, read from the vendored files; reaching the driver's device is a matter of its ACL, which names SYSTEM), `SeShutdownPrivilege`, `SeSystemtimePrivilege`, `SeTimeZonePrivilege`, `SeSystemEnvironmentPrivilege`, `SeCreatePagefilePrivilege`, `SeLockMemoryPrivilege`, `SeProfileSingleProcessPrivilege`, `SeSystemProfilePrivilege`, `SeIncreaseBasePriorityPrivilege` (no `SetPriorityClass`), `SeIncreaseWorkingSetPrivilege`, `SeManageVolumePrivilege`, `SeCreatePermanentPrivilege`, `SeCreateSymbolicLinkPrivilege` (Koppel refuses links and never makes one) and `SeDelegateSessionUserImpersonatePrivilege`. None of these is used anywhere in the repository. That the device's ACL names SYSTEM is taken from usbip-win2's documentation and was not read from the driver.
  - **Case against.** A list that is too short breaks something at run time, and it breaks it for the person with no hint: a tray that does not appear (the first three), a start that fails on a custom config folder (the last two). The four unsure ones are kept for that reason, which also means the service is still more privileged than it needs to be, by those four. What would change the pick: the install test in `installers.md` shows the service, the tray, Restart Koppel, a USB attach and a custom `Paths:Config` working with the list, and a second round without the unsure ones passing the same checks.
  - **Undo.** The list is the `RequiredPrivileges` value (REG_MULTI_SZ) under `HKLM\SYSTEM\CurrentControlSet\Services\Koppel`. Without it the service gets the privileges of its account again at its next start (Microsoft's documentation, not run here).
- **One data folder implementation: `koppel prepare-data-folder`.** The PowerShell script the installer used to carry is gone. `koppel-config/src/data_folder.rs` has the rules, ported one for one from the script (read from it as it was at 0.2.0): refuse a file or a link; an administrator is SYSTEM, Administrators, TrustedInstaller, a direct member of the local Administrators group or a member through a group; take over a folder an administrator owns (owner to Administrators, protected ACL for SYSTEM and Administrators only, down the whole tree), delete a link inside (the link, never its target), rename aside whatever no administrator owns (`<name>.not-admin-owned-<time>`), create a missing folder the same way, and `--check` changes nothing. `harden_directory` (what the service runs at every start) and the command now call the same `protect` function in `koppel-config/src/harden.rs`, so the ACL is written in one place. The installer runs `Koppel.exe prepare-data-folder` as the same custom action, with the same exit codes (0 safe, 1 not) and messages, and `driver.ps1` calls `--check`. What changed on purpose, and why:
  - **The group lookups use the Net APIs, not ADSI and an S4U logon.** `NetLocalGroupGetMembers` at level 0 gives the SIDs without resolving names, so a member with no name here still counts: on the development PC it lists three `S-1-12-1-*` AzureAD SIDs, and `AzureAD\RikusvanRensburg`, whose folder `--check` accepted. A member through a group is read with `NetUserGetLocalGroups` and the indirect flag, which covers local accounts that are not signed in and nested groups. The script's S4U `WindowsIdentity` covered domain accounts by asking a domain controller; this asks the local machine, which for a domain account also needs a domain controller, and was only tried here on local and AzureAD accounts. A lookup that fails means "not shown to be an administrator", as before; an unreadable Administrators group is an error, not a yes.
  - **A process that is not elevated is refused by the command, and keeps its own access in `protect`.** The script would fail at `SetOwner`. The command now says to run it as an administrator, before it touches anything. `protect` itself, as `harden_directory` always did, leaves the owner and adds the current user when the process cannot give an owner away, which the unelevated tests rely on.
  - **The aside name is UTC with milliseconds** (`utc_stamp`, as the config files use), not local time to the second, so two items renamed in one second do not collide.
  - **A link where the folder should be is refused even when its target is gone.** The script's `Test-Path` said "missing" for a dangling junction and `New-Item` then failed with an unhelpful message.
  - **What was not changed:** an item whose owner cannot be read stops the run, as `Get-Acl` throwing did. Windows pushes inheritable entries down on its own when a folder's ACL is set, so an item renamed aside can still show changed inherited entries; the run itself never calls `protect` on it or gives it away (a test holds that, on a real folder).
  - **Tested.** The rules run on Linux and Windows against real temp folders with owners and group membership injected through the `Accounts` and `Files` traits (a SYSTEM-owned folder cannot be made unelevated). On Windows the ACL application, link deletion and rename aside also run for real, and the real Net lookups are checked against SYSTEM, Administrators, TrustedInstaller, Everyone and an account that does not exist. Not tested without an install: a folder really owned by SYSTEM or by a non-administrator other than the current user, the installer calling the command, and a domain account.
- **Compose: `restart: always` is kept** and the Dockerfile comment now says so (it said `unless-stopped`). Each compose gets a `json-file` log limit of three files of 10 MB.

## UI sessions in memory (2026-11-12, #148)

- **A table in memory, not a signed cookie.** A session is a 256-bit random id and an entry in a `HashMap` (12 hours without use, 7 days at most, a `CancellationToken`). It replaces an HMAC cookie with a key file, a security stamp, a map of the session to keep per stamp and a list of signed-out ids in `ui-auth.json` that was scanned linearly on every request. Case against: a restart signs everyone out, and two Koppels behind one name would not share sessions. Neither matters for one admin on a LAN, and the sign-in is one password. What would change it: a deployment with several instances behind a balancer, or an admin who restarts often and says so.
- **Opaque ids, not sealed ones.** The table is the authority, so the cookie carries nothing to forge or to decrypt, and ending a session is deleting an entry, which is also what makes a copy of the cookie useless.
- **`cookie` 0.18 (locked at 0.18.2) for the header** (MIT OR Apache-2.0, both already in `deny.toml` and `about.toml`; default features off, so no percent-encoding, signing or jar). Picked over writing the `Set-Cookie` string by hand, which the old code did, because the attribute rules (`__Host-` needs `Secure`, `Path=/` and no `Domain`) and the parsing of a `Cookie` header with several pairs are easy to get subtly wrong; `cookie` is the crate axum-extra, actix and reqwest use for it, and it sits on the `time` already here. Considered: `axum-extra`'s `CookieJar` (pulls more of axum-extra than the one header needs).
- **Cookie `__Host-koppel-session`.** A new name, so there is one forced sign-in at the upgrade, and the `__Host-` prefix so a browser takes it only from this origin over HTTPS.
- **The sessions are capped at 256.** Signing in needs the password, so nothing reaches the cap but the owner's own habits; evicting the session that would end first keeps the table bounded without a refusal.
- **`ui-auth.json` is kept, `ui-session.key` is deleted.** The issue said to delete both, but `ui-auth.json` holds the password hash: deleting it would drop the password. It is no longer written for sessions and its stamp and revoked list are read past. `ui-session.key` is deleted at the first start.
- **A password changed from outside ends every session** (the file's watcher compares the hash with the one this server last wrote), which is what the stamp did for a reset or a hand edit.

## Serving, stopping and limits (2026-11-12, #151)

- **A cap of 512 connections per listener, held as a semaphore the accept loop takes before it accepts.** The rest wait in the kernel's backlog (1024), so nothing grows here and nothing is refused with an error the client has to understand. Case against: a client that holds 512 idle connections starves the others until the handshake timeout or its own keep-alive drops them. An admin and a few clients need a handful, and a limit per address would be the next step (what would change it: a report of it). 512 and not more because a service often starts with 1024 open files.
- **The live push ends on a token the accept loop puts on each request, not on a handle in `App`.** The loop owns the stop, and `App::stop` runs after it, so a token from `App` would be cancelled too late to matter. A request without the token (a test calling the router) gets one that is never cancelled.
- **Timeouts on the UI router only.** The body-read timeout is idle time between pieces, not the whole body. The network router would cut gRPC streams that are quiet between messages, so it has none; Skakel limits its own calls.
- **Tested in two ways.** The stream and the body timeout are tested with a paused clock (`start_paused`), where the elapsed time says whether it ended by itself or by running out. The stop with a real connection is tested in real time with a margin against the 3 second grace, because a paused clock jumps ahead whenever the runtime waits for the network.

## Tasks have an owner (2026-11-13, #151)

- **One `Tasks` (a `CancellationToken` and a `TaskTracker`) in `App`, handed to the roles that start tasks.** `Tasks::spawn` ends the task when its work ends or the app stops. `App::stop` stops the roles in order as before, then cancels the token and waits for the tracker for at most 5 seconds, then stops the config files. A task still running after that is logged with a count and left to the runtime. It replaces the `stoppers` list, whose only entries were the config files (now a plain `Files` struct), and the bare `tokio::spawn` calls in the Skakel client, links, streams and the server's event reader. The systemd heartbeat in `koppel` joins the `JoinSet` of the listeners and ends on the same stop.
- **Case against: a token that cancels everything at the end could cut a stream's last frames.** It cannot at a normal stop, because the data plane and the USB client close their streams first and the pumps end by themselves. The token is the backstop for what a role forgot.
- **`SkakelServerRole` answers after its server stopped.** Its handle lookups return nothing instead of panicking: reads show an empty list (the keys view falls back to the store's certificate), changes fail with `RoleError::NotRunning` (500, as any failed save). A request that was in flight at the stop used to panic on its task.
- **Hashing a password returns an error** when the blocking task does not finish (a runtime shutting down), as 500 on the setup and change calls, instead of a panic.

## Wire types generated from the Rust DTOs (2026-11-13, #137)

- **ts-rs 12.0.1 (MIT) over specta.** Both derive TypeScript from serde types. ts-rs is a stable release (12.x) that reads `rename_all`, `rename`, `alias` and `default` straight from serde, has a small tree (`ts-rs`, `ts-rs-macros`, `termcolor`) and no runtime registry. specta is still `2.0.0-rc` with a separate `specta-typescript` at `0.0.x`: its API moves between releases, and its strength (one type registry for several exporters, tauri-specta) is something Koppel does not use. What would change it: ts-rs dropping serde compatibility, or a second target language.
- **One generated file, written by a test.** `koppel-web/src/wire.rs` collects every type the UI reads or sends, writes their declarations to `ui/app/src/api/generated/wire.ts`, and `generated_types_are_current` fails when the checked-in file differs. Regenerate with `KOPPEL_WRITE_WIRE=1 cargo test -p koppel-web wire`. There is no CI, so this runs with `cargo test` like the rest. ts-rs's own `#[ts(export)]` writes one file per type from each crate's tests; one file from one test is simpler to check for drift and to import.
- **Dates are `string`.** ts-rs does not read `time::serde::rfc3339`, so those fields carry `#[ts(type = "string")]`. The fixtures test below pins what the strings look like.
- **Shared JSON fixtures.** `ui/app/src/test/wire/*.json` is read two ways. The Rust test `the_fixtures_are_what_rust_sends` reads each into the Rust type and writes it back, and the JSON must come out the same: a field renamed, added or dropped, or an enum word the Rust side does not know, fails. The UI mocks (`test/wire.ts`) check each fixture against the generated type, so a missing field or a field of another type fails the typecheck. The types read the fixtures with `Deserialize`, derived only in tests for the web crate's own types (`cfg_attr(test, ...)`) and always for koppel-usb's, which already had it on `DeviceView`.
- **`DeviceView.speed` stays a string.** It is the label the domain layer builds ("USB 2.0 (480 Mbit/s)") and the UI shows it as it is; an enum would need the UI to hold the labels, a wire and a copy change for no gain. The other state words (`DeviceState`, `LinkState`, `PairingState`, `RequestState`, `Outcome`, `EntityKind`) were enums already and now reach the UI as unions.
- **No runtime check in the browser.** `readJson<T>` types the body; it does not validate it. A zod-style schema would be a second description of every type. The Rust fixtures test and the typecheck cover the drift that matters here, between two halves built together.

## koppel-web small items (2026-11-13, #157)

- **The push payloads are an `Event` enum with one variant per name, but the name stays outside the JSON.** `#[serde(tag, content)]` would write the name into the data (`{"event":"SettingsChanged","data":{...}}`). The UI listens with `addEventListener(name)` and reads each event's data as the value itself (`push-table.ts`), and the tray reads the name from the SSE event too, so the tag form would change the wire on the server, the UI, the tray and the contract tests, which this issue does not do. The enum is `#[serde(untagged)]` with a `name()`: each name has one payload type, a call cannot send the wrong one, the UI and the contract tests are untouched. Sending now skips the JSON when no stream and no tray is subscribed. A snapshot first on connect is not done here (it needs the wire change, see the live-layer issue).
- **`JsonBody` and the query parser stay hand-written.** Measured on a release build with the size profile (`opt-level = "z"`, fat LTO, one codegen unit, Windows x64, the UI replaced by a one line page in all three so the difference is only code): 8,294,400 bytes as it is; 8,302,080 (+7.5 KB) with axum's `query` feature and `Query<T>` for `/api/activity` in place of `parse_query` and `decode`; 8,334,336 (+39 KB in all, so +31 KB for it) with `Json<T>` as well, inside a wrapper that keeps the statuses. axum's `json` feature is already on through tonic, so the cost is the extractor's own code (it keeps the error path with `serde_path_to_error`). The bytes are not worth what they replace: 40 lines that are tested, and the hand-written `JsonBody` keeps behaviour 0.1.x clients rely on (the byte order mark is skipped, a missing body and a bad one are a bare 400, a wrong content type is 415 with no body), which `Json<T>` would change. What would change it: a new endpoint that takes a real query, where `Query<T>` pays for itself.
- **One `Unpoisoned` helper for the locks of koppel-web, not `parking_lot`.** `Mutex::locked()` and `RwLock::read_locked()` / `write_locked()` take the guard of a poisoned lock, as the 35 sites did by hand. `parking_lot` would do the same without poisoning but is a dependency, a second kind of guard, and it changes every type that holds a `std` lock. koppel-config, koppel-usb and koppel-windows keep their own few sites.
- **`ETag` on the files that keep their name** (index.html, the icon): the first 16 bytes of the SHA-256 that `rust-embed` already has for each file, one tag for the gzip copy and one for the inflated copy of the same file. A matching `If-None-Match` gets 304. The hashed files under `assets/` stay `immutable`.
- **`ui_url::checked` and `opener::host_and_port` use the `url` crate** (already in the build through Skakel's client). The crate lets a quote through in a host, so `checked` still refuses a quote, whitespace or a control character in the result: that is what keeps the launcher's quoted argument whole.

## The API under /api/v1, with problem JSON (2026-11-13, #138)

- **One `ApiError`, written as RFC 9457.** Three cases: `Validation` (400, each field with its messages), `Refused` (a status, a stable `code` and a sentence) and `Internal` (a `thiserror` source chain, logged whole, answered as a 500 with a fixed sentence). `type` is always `about:blank`: no problem has a page of its own to point at, and `code` is what a client branches on. The sign-in refusals used to be `{ error }` and validation used ASP.NET's `ValidationProblem` text; both are this shape now, so the UI reads one thing (`problemMessage` in `api/http.ts`: the first field message, else `detail`).
- **A refusal for what used to be a bare status.** The origin check (403), the sign-in rate limit (429), the missing session (401), the API's own unknown path (404) and a body that is missing, not JSON or not sent as JSON (400, 415) carry a problem body now. Not changed: `role_gate`, which the network surface shares with the UI and which stays a bare 404 so that surface tells a caller nothing, and the layers around the whole router (the 408 from the timeout, the address checks), which are not the API's.
- **Case against the 500 sentence being fixed:** a person at the UI cannot see why a save failed. It is a disk or a lock, the log has it, and echoing an error text to a browser is how paths and internals leak. What would change it: a report of a failure the person could fix from the message.
- **Paths are resources, the verb is the method.** `POST .../clients/{id}/secret` (was `rotate`), `PUT`/`DELETE .../devices/{busId}/attachment` (was `attach`/`detach`), `PUT`/`DELETE .../pairing/window` (the open was a `POST`), `POST .../pairing/requests/{id}/approval` and `DELETE .../pairing/requests/{id}` (was `approve`/`deny`), `POST .../pairing/confirmation` (was `confirm`) and `PUT .../keys/current-certificate` (was `next-certificate/switch`: it makes the prepared one the current one). Left as they are: the sign-in paths (`/auth/login`, `/auth/logout`, `/auth/setup`, `/auth/password`), which the guards and rate limit are written against and whose verbs are what a person calls them, and `/client/connection/test`, where "test" is the resource it creates.
- **No old paths answer.** The UI is embedded in the program, so it always matches the server it came from, and no other client of `/api` is known. `/api/remote/*` is the network surface's protocol with other Koppels, not this API, and does not move. Case against: a script someone wrote against 0.2.0's REST paths breaks at the upgrade, and the changelog says so. What would change it: a report of one, and then the old paths would answer for one release.
- **Dates needed no change.** Every date the API sends is `time::serde::rfc3339` (`Z` form since #144); the contract tests accept any RFC 3339 offset, and the fixtures round trip pins the form.
- **`Json<T>` answers `application/json` without a charset,** where the old helper wrote `; charset=utf-8`. JSON is UTF-8 by definition (RFC 8259), so nothing reads the difference.

## `/readyz` and build info (2026-11-13, #154)

- **`/readyz` is a second endpoint, `/healthz` stays as it is.** The watchdog and the Docker check ask whether the process serves requests, and a USB gateway whose port is taken must not get Koppel restarted, because a restart does not free the port and drops every attached device. `/readyz` is for a person or a monitor. It answers 503 when the gateway is faulted or no certificate is loaded, 200 otherwise, with the states as JSON.
- **The link state is reported and does not decide `ready`.** A client whose server is switched off is working, and a readiness check that fails for it would wake someone for a thing Koppel cannot fix. A monitor that cares reads `link`. Case against: a stuck link (connecting for hours) looks ready. The field is there for that, and a rule on its duration needs a clock the server does not keep yet.
- **It names states and no messages.** Anyone `Ui:AllowFrom` lets in can read it without signing in, so it carries no fault text, address, fingerprint or file name. The reason for a gateway fault is on the devices page and in the log.
- **Build info is `commit` and `built` in `/api/system/info`,** from the same build script as `koppel --version` (`KOPPEL_COMMIT`, `KOPPEL_BUILT`). The UI shows it as a Build fact in the side panel with the version. The status card at the foot of the sidebar is a `@koppel/react-ui` component with one version slot, and a second line there is a primitive change for the design system, not for this issue.

## The client tests on the paused clock (2026-11-13, #140)

- **A kernel attach has an in-memory form behind `test-util`.** The client's attach made a pair of loopback sockets and handed one to the attacher, so every client test waited on real I/O, and a paused clock jumps ahead while the runtime waits for a socket (the reply is in flight, the clock has already run out the deadline). `UsbAttacher` gets two methods behind the feature, `in_memory()` and `attach_in_memory(end, ...)`, that default to "no". An attacher that says yes is handed one end of a `tokio::io::duplex` pipe, and the relay gets the other. Nothing changes without the feature: the code path is `loopback_pair` as before, and the production attachers do not know the methods.
- **The tests use it through `FakeKernel::in_memory()`.** Twelve tests of `tests/client.rs` run on `start_paused` now (the deadline, the detaches, the changed connection, the stop, the saves): the server was already in memory (`MemoryLinks`), and the config files go through `spawn_blocking`, which tokio does not let the clock jump past. They take milliseconds, `eventually` and the 3 second deadline wait in virtual time, and 25 runs in a row passed.
- **Real-socket tests stay.** `changing_the_connection_detaches_what_was_attached_over_a_real_socket` and the three-cycle detach and attach again over real sockets are the old tests, kept in real time because a socket pair is what an attach does on a machine, and the gateway, the USB/IP driver (`client_driver.rs`) and the end to end tests (`end_to_end.rs`) need real listeners.
- **Case against:** the in-memory path is not what runs in production, so a bug in `loopback_pair` or in the blocking attach would not show in the paused tests. The kept real-socket tests, `end_to_end.rs` and the sysfs tests are what cover that. What would change it: a kernel attach failing in the field that only the memory path hides.

## What was left of koppel-web (2026-11-13, #157)

- **`confirm_pairing` answers 202 and the confirm rule stays.** The save runs after the answer, so the 202 says the person's choice was taken, not that the connection was saved, which is what every other change here says too. Answering after the save would make the request wait on a disk write with the UI showing nothing, and it would be the one change that answers differently. A failed save is not lost to a client that missed the push: the run's status is set to `failed` with the message ("Could not save the connection to ...") in the same place `GET /api/v1/client/pairing` reads, and it stays there until the person starts or cancels a pairing. A stream that opens after the failure also starts with it (`PairingStatusChanged` in the snapshot). Read from `SkakelClientRole::confirm_pairing` and `pairing()`; a failing save is not tested, because the config file cannot be made to fail from a test here. What a real run would settle: nothing about the rule, only the wording of the failure on a full disk.
- **Pairing has its own validation (`PairStart::validate`).** It used to build a `ConnectionUpdate` with the made-up client ID "pairing" to reuse `validate()`. The address and fingerprint checks are one function (`server_problems`) that both types call, so the messages cannot drift, and pairing no longer pretends to have a client ID.
- **A real Content-Security-Policy, on every answer by the security headers layer.** `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. Read from the Vite build: `index.html` has no inline script or style, the fonts are files under `assets/` (no `data:` URLs, so `font-src` needs only `'self'`), the stylesheet is a `<link>`, and the live push is an `EventSource` on the same origin (`connect-src 'self'`). The one inline need is styles: react-aria adds `<style>` elements at run time (text selection while a press is held, drag and drop), and React's `style` props are set through the DOM, which a CSP does not block. So `style-src` keeps `'unsafe-inline'` and scripts never do. Case against: inline styles allow CSS injection if an injection exists. A nonce would need a fresh `index.html` per request (react-aria reads it from a `<meta>`), which ends the ETag and 304 from #157's first round, for a page with no known way to inject markup and a script policy that already blocks the worse half. What would change it: react-aria dropping its injected styles, or a page that renders untrusted HTML. Checked in headless Chromium against a real `koppel` on loopback: the first-run setup, the role step and the signed-in app loaded with no violation event, all five font files loaded, the live indicator reached "Live". Not checked: every page and dialog (the Devices, Configuration and Activity pages and the pairing flow were not opened).
- **Snapshot first on connect.** A new `GET /api/v1/events` stream subscribes, reads the state where the GET routes read it, and sends one event per resource of the role first, under the names the changes use. No new name and no new payload, so `wire.ts` and the fixtures did not change; what changed is that a stream starts with events. The UI's reconnect fetches only what the snapshot does not cover (`notInSnapshot` in `push-table.ts`) instead of everything. Case against: a snapshot event looks like a change, so it could confirm a pending change that was not saved. It cannot, because it carries what the server holds now, which is what the confirm rule compares with, and `SettingsChanged` and `ConnectionChanged` are sent from the config file's own state. The one visible effect of reusing the names is that a test that waits for any `DevicesChanged` must read the snapshot first; the contract tests' `open` does. The tray subscribes to the push inside the process and does not get a snapshot. What would change it: a reader that needs to tell the snapshot from a change would need a marker event, and none does now.
- **The USB data path copies.** `Frames` carries `Bytes` both ways: the `data.to_vec()` on receive is gone (a `Bytes` writes to the pipe as a slice), and the `buffer[..read].to_vec()` on send is gone, because frames are `split().freeze()` slices of one `BytesMut` that `read_buf` fills, so small reads (USB/IP headers) share an allocation and a large one is not copied. `bytes` becomes a direct dependency at the version already locked (MIT, already allowed). A test sends sizes from 1 byte to three chunks and a bit through two ends and compares every byte. What stays: the pipe itself is a copy in and a copy out (`tokio::io::duplex`), and so are the two tasks per stream; removing them means koppel-usb reading frames directly, a change to its `DeviceStream` trait. They stay until a measurement on a Raspberry Pi says the copies or the task switches show next to the USB/IP round trips, which only that hardware can say.

## Crates cut by concern (2026-11-13, #150)

- **koppel-usb follows `Observed` values and saves into `Store`s, and names no config file (first step).** `UsbSettings` (role and share-on-startup), `Connection`, `SharedDevices` and `AttachedDevices` are koppel-usb's own types, shaped like the files' but without serde, and `koppel-web/src/roles/usb_store.rs` converts at the edge. The one real cost is the duplication of five small types. Case against it: the config types could be used directly if koppel-config were below koppel-usb, but then the USB layer knows the file format, which is what the issue wants gone.
- **`Observed` is a subscription with an acknowledgement, not a `watch::Receiver<Role>`.** The issue suggested a watch channel. A watch cannot say when the receiver has applied a value, and today `ConfigFile::update` returns only after every subscriber has (the data plane has ended its sessions, the client has released what it held), which is what the UI's confirmation and the tests that change the role rely on. `Observed::subscribe` takes an async handler that the file awaits, so nothing changes. Case against: a watch is simpler for a consumer that does not care. What would change it: a role that must not hold up a settings update, none today. The drop of the returned `Subscription` ends it, so no role needs an unsubscribe call.
- **`koppel-secrets` is a leaf crate with `Secret<T>` only, made in this step.** `Connection` carries the client secret, and koppel-usb compares it and passes it to the transport. It needs the type that redacts and wipes, without the config crate that holds the secret files. `koppel-config` re-exports `Secret`, so nothing that uses `koppel_config::Secret` changes. Whether `SecretBox` and the rest of the secrets code join it is the step 4 question and is decided there.
- **koppel-usb's tests keep real config files.** They dev-depend on koppel-config and carry a test copy of the glue (`tests/common/files.rs`), because they check what lands in `devices.json` and `attached.json` and what a corrupt file does. Production code in koppel-usb does not import koppel-config; only the tests do. Case against: the copy can drift from the program's glue. The contract tests drive the program's own glue end to end.
- **The `usbip` crate holds the protocol, the bus ID, the device model and the relay (second step).** The messages are written in terms of `UsbDevice`, `UsbInterface` and `UsbSpeed`, so those moved with them, and the export status and virtual port types stayed in the same file because they are what the kernel's sysfs files say about the same devices. koppel-usb re-exports all of it, so its modules and the crates above it did not change their imports. The unconditional re-export makes the device types public in koppel-usb where only `test-util` did before; they are public in `usbip` anyway.
- **`relay` takes a future to stop on, not a `CancellationToken`.** The issue wants no `tokio-util` in `usbip`. A call is now `usbip::relay(a, b, stop.cancelled())`, which is the same thing. The two relay tests moved with it and use `tokio::io::duplex` where they used koppel-usb's in-memory stream pair, and one test is new for the stop future.
- **The stream traits stay in koppel-usb.** `DeviceStream`, `StreamOpener`, `CloseReason` and `OpenError` have no Koppel dependency, but they are the roles' view of the transport (`CloseReason::Stopping` is Skakel's close, the doc says who opens them), not USB/IP, which has no such thing: the kernel's protocol runs over a plain socket. Case against: they would be free to move. What would change it: a second user of the traits outside koppel-usb.

### Third step: `koppel-app` between the web server and the USB layer

- **The roles, the activity log, the push bus, the connection view and the tray rules moved out of `koppel-web` into `koppel-app`; `koppel-web` keeps the routes, layers, sign-in, TLS ports and the UI.** The tray belongs with the roles because its rules read the activity log, the pairing requests and the USB views, all of which are roles' output, and the only web thing it read was the sign-in. That one dependency is a trait now (`SignInState`, implemented by `UiAuth`), so `koppel-windows` depends on `koppel-app` and no longer on the web server: the service takes a `TrayFeed` (`App::tray_feed()` in koppel-web builds it). It could have gone into `koppel-windows` instead, but the rules run and are tested on every platform and so would have made that crate carry cross-platform logic next to its Windows-only code.
- **`App` is two types.** `koppel_app::App` opens the config files and starts the roles; `koppel_web::App` holds it with the sign-in, the access rule, the rate limit and the acceptors and builds the routers. Its `start` and `stop`, `tls()` and `certificate()` are unchanged, so `koppel` and the contract tests did not change their calls (only `service.started` takes the feed now). `ui-auth.json` is opened before the roles and stopped after them, as the other files are.
- **Moved with them because both layers use them:** `ConnectionView` and `ConnectionUpdate` (the REST body, and what pairing saves through the same rules), `is_grpc_path` (the server role refuses a gRPC call that came while it is off), `random_bytes` and `hex`, the `Unpoisoned` lock helpers, `Tasks` and `Host`. `CertificateSlot` is in `koppel-app` because Skakel's store makes it; `koppel-web::tls` re-exports it and keeps the acceptors and `self_signed`.
- **Case against:** more public surface (what was `pub(crate)` in the roles is `pub` in `koppel-app`, since the web crate is now outside), and a role's view types that the API serialises now sit two crates from the handlers. What would change it: a second program that needs the roles without the web server would be the proof it was worth it, and a third crate that wants only the tray would argue for `koppel-tray`. Neither exists.
- **The wire types read back under a feature.** The API tests deserialise some wire types, which was `#[cfg(test)]` inside one crate. They are `cfg_attr(any(test, feature = "test-util"), derive(Deserialize))` in `koppel-app` now, and `koppel-web` enables the feature for its tests only.

### Fourth and fifth step: no `koppel-state` and `koppel-secrets` split, and the Windows crate out of the default members

- **`koppel-config` stays one crate.** The issue asked for `koppel-state` (typed files and `ConfigFile`) and `koppel-secrets` (`SecretBox`, hardening, DPAPI, key sources) only if the dependency graph shows a benefit once the other cuts are in. It does not. Read from `cargo tree` and the imports after the first three steps: `koppel-usb` depends on `koppel-secrets` (the `Secret<T>` leaf made in step 1) and on no config code; `koppel-upgrade` uses `KoppelPaths`, `SecretBox`, `SecretFormat`, `replace_file`, `utc_stamp`, `ServerSecrets` and DPAPI, so it needs both halves; `koppel-app`, `koppel-web` and `koppel` open the config files with `SecretBox` codecs, so they need both too. No crate would depend on one half only, so the split would add a crate and change no build. It would also have a cycle to cut: `SecretBox::codec()` implements `ConfigFile`'s `FileCodec`, and the key file and the config files share `write_atomic`, `create_private` and `sync_directory`. The `Secret<T>` leaf is the one part where a half was wanted, and it is its own crate already. Case against: the secret code (about 900 lines, DPAPI, key sources) is a security-sensitive unit that would be easier to review apart. What would change it: a crate that needs to seal a value but not read the config files, such as a second tool that reads `secrets.json`.
- **`koppel-config` has no dev-dependency on `koppel-web` any more.** Its certificate test had moved to `koppel-upgrade` earlier and the dev-dependency, with `tokio-rustls`, was left behind; it is removed here, and `cargo tree` shows no path from `koppel-config` to a crate above it. `koppel-upgrade` still has one: `tests/certificate.rs` checks that the web server presents a certificate carried over from 0.1.x, through `koppel_web::tls::acceptor`. It is a test, not production code, and moving it into `koppel-web` would need that crate to dev-depend on `koppel-upgrade` and its fixtures instead, the same edge the other way, so it stays.
- **`koppel-windows` is left out of `default-members`.** Cargo cannot make a `[[bin]]` or a member depend on the target, so the choices were a feature that every Windows build then has to turn on, or leaving the member out of the defaults. The second is one line and the Windows installer script already names `-p koppel -p koppel-windows`. A plain `cargo build` or `cargo test` on Windows skips the tray program and the crate's tests now, which is why CLAUDE.md and the docs say `--workspace` for the checks. The Docker build compiles `-p koppel` only and copies `koppel-windows` because Cargo reads every member; the COPY list names every crate (`koppel-app`, `koppel-secrets` and `usbip` were added with their steps). Case against: someone running `cargo test` on Windows without `--workspace` gets less than before. What would change it: the crate holding Linux-testable code only (`wire`, the log file's writer) moving elsewhere, after which the crate could be Windows-only and cfg'd out whole.

## Root takes over a folder of uid 1654 (2026-11-13, #214)

- **When Koppel runs as root and the config or keys folder belongs to uid 1654, it takes the folder over.** The folder and everything under it is given to root (links are changed, never followed), one INFO line says what was taken over and why, and the start goes on. Every other foreign owner is still refused, now with a message that gives the Docker and host-path fix. The decision is `decide_owner(owner, running)` in `koppel-config/src/harden.rs`, a pure function with a unit test per branch. A volume made by the 0.1.x image has its folders owned by 1654 (the image's `app` user) while the compose runs Koppel as root, so 0.2.1 crash-looped on every Docker install that began on 0.1.x, and 0.2.0 had started on the same volume. Checked in a Linux container: a folder really owned by 1654 is taken over, one owned by 4242 is refused.
- **Case against.** The owner check exists because a folder's owner can swap what is in it, and any process running as uid 1654 on the host could have written there before the take over. It is narrow: 1654 is only ever the old image's user, the files in it are sealed with a key that is in the same volume or outside it, and root can read everything in the folder anyway, so the take over gives a 1654 process nothing it did not already hold except the chance of having planted a file. Another uid, and any non-root run, still gets the refusal. What would change it: a host that runs something else as 1654 and mounts the same folder, which the owner would then fix by hand with the command in the message.
