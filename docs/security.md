# Security

## Auth

The certificate, the registered clients, the tokens, revoking and rotating are Skakel's; see "Tokens" and
"Certificates" in Skakel's [`docs/protocol.md`](https://github.com/matumi-software/skakel/blob/main/docs/protocol.md). What Koppel does with them:

- **Certificate:** Koppel makes a self-signed certificate on first start (`koppel-web`, with rcgen, as Skakel makes its own), valid for ten years. Every HTTPS port presents it, UI included, the current one at each handshake. Its SHA-256 fingerprint shows in the server's Clients section.
- **Clients:** the server admin adds a client by name and gets a client ID and secret. Skakel takes control and format characters out of the name; a name with nothing left gets 400. Koppel sets Skakel's `KeepClientSecrets`, so the secret is kept inside the encrypted `secrets.json` and the admin can copy it again later from the client's row.
- **Revoking and rotating:** both block the client at once, everywhere: its tokens, its hub connections and its USB streams. Skakel tells the client why, and Koppel's client shows that it has to pair again.
- **Tokens:** OAuth 2.0 client credentials from Skakel, 30 minutes, over HTTPS only. Koppel's `/api/remote/*` takes them. A token is a random string the server remembers, not a signed one, so there is no signing key to keep or rotate, and a server that restarts forgets its tokens (clients ask again).
- **Pairing window:** Skakel 0.3.0 takes new pairing requests only while a person has opened a window on the server's Clients page (10 minutes by default, 1 to 60). Outside it a pairing request gets 403 and spends no limit, so a stranger on the network cannot fill the server's list of requests while nobody is at it. The window is closed after every start and when the role leaves the server side.

### Rotating the certificate

It is replaced from the server's Clients section. Each action answers 202 and is
confirmed by `ServerKeysChanged`, like any other change, and each is an activity entry.

- **Certificate, in two steps,** because clients pin it: Prepare makes the next certificate and Skakel tells the linked clients its fingerprint over the remote hub. The Clients section shows who has it. Switch presents it at once; switching before every client has it is allowed, after a warning. Cancel drops it. A restart anywhere in between changes nothing, because it is all in `secrets.json`.
- **On the client:** the link saves what it learns in `connection.json`: the next fingerprint as a second trusted one (`ClientConnection.NextServerFingerprint`), and after the switch the new pinned one. Only once that is saved does the link tell the server it has it. The same credentials with the fingerprint moved on to the one it was told about is the same server (`ClientConnection.Continues`): the link and the attached devices carry on, and `attached.json` moves to the new fingerprint.
- **A client offline the whole time** never hears of the next certificate. After the switch it reports `certificateMismatch`, as for any certificate it does not know, and must be paired again or given the new fingerprint under Configuration (the stored secret carries over when the new fingerprint is the one that server announced).

### UI sign-in

The UI on port 5240 (HTTPS) needs a password. There is one admin password and no user name.

- **First run:** whoever opens the UI first sets the password, as in Home Assistant, Jellyfin and Portainer, except where a setup token is required (see below). To limit who that can be, setup is open only for a window (`KOPPEL_UI_SETUP_WINDOW_MINUTES`, 10 minutes), as Portainer does: from when Koppel starts without a password, or from a reset while it runs. While it is open, `POST /api/v1/auth/setup` takes only `{ password }` and signs that browser in. After the window it answers 403 with "Setup has timed out", and the UI says to restart Koppel. With a password set it answers 409. `GET /api/v1/auth/state` carries `setupOpen` and `setupUntil` (when setup closes, or closed; null once there is a password), and `setupTokenRequired` (whether setup asks for the token below), so the first-run screen asks for the password, and the token where it is required, or explains the timeout. While no password is set the UI asks for the state every 15 seconds, so it notices the timeout, or someone else setting the password first.
  - The log says once, at Warning, that Koppel is waiting for its first password, at `https://<machine>:<KOPPEL_UI_PORT>`, and until when. Who set the password is logged too.
  - **Setup token (Linux and Docker):** when `KOPPEL_UI_ALLOW_FROM` is `lan` or `any`, anyone the setting admits could otherwise claim the machine in the window, so setup needs a token. Koppel makes 128 random bits as 32 hex digits each time the window opens (a start without a password, or a reset), and prints it in the same Warning line (`docker compose logs koppel`, `journalctl -u koppel`). `POST /api/v1/auth/setup` takes `{ password, setupToken }`; without the right token it answers 403, before the password is looked at, and the UI shows a field for it where `GET /api/v1/auth/state` says `setupTokenRequired`. Whoever can read the log owns the machine, as whoever can run the reset command does. The token works once: it is gone when the password is set, and a reset makes a new one. With `KOPPEL_UI_ALLOW_FROM=local` there is no token, since only this machine can reach setup. **Windows keeps the first-caller rule, with no token:** the installer sets `local`, and a service has no console to read a token from (the earlier setup code was removed for that reason).
  - `KOPPEL_UI_ALLOW_FROM` applies to setup as to the rest of the UI, so a native Windows install (`local`) can only be set up from that machine.
  - Earlier builds wrote a setup code to `setup-code.txt`. Koppel deletes that file on start.
  - Setup is step 1 of the first-run wizard in the UI.
- **Password:** at least 10 characters, at most 128, and not "koppel" or "password" in any case. It is hashed with PBKDF2-SHA256, 600,000 iterations and a 16 byte salt, and kept in the encrypted `ui-auth.json`, which holds nothing else.
- **Cookie:** `__Host-koppel-session`, HttpOnly, SameSite=Strict, Secure (the UI is HTTPS only) and `Path=/`, with no `Domain`: the `__Host-` prefix makes a browser take it only from a secure origin and refuse one a sibling host sets. It is a session cookie, and its value is an opaque id, 256 random bits as 43 URL-safe base64 characters, that means nothing without the server's table. The cookie is formatted and read with the `cookie` crate. A session lasts 12 hours without use and a request in its second half extends it, and it never lasts more than 7 days after the sign-in (the password change does not restart that). An API call that is not signed in gets 401, never a redirect. 0.1.x and 0.2.0 named the cookie `koppel.ui`; that one is ignored, so everyone signs in once at the upgrade.
- **Backoff:** login and password change lock a caller for one minute after 5 wrong tries, and double the lock on each further failure, up to one hour. A caller is one IPv4 address, an IPv4-mapped IPv6 address counting as its IPv4 address, or one whole IPv6 /64: a host owns its whole /64 and can take any address in it, so counting whole addresses would let one neighbour rotate past the lock. A shared /64 therefore shares its lock, so one host's wrong passwords can lock the others on that network out (the rate limit below still counts whole addresses). A try is counted before the password is hashed and given back when it is right, so parallel guesses cannot all get in ahead of the lock. The lock applies before the password is looked at, so a right guess during it is refused too. Setup has nothing to guess, so it has no backoff; the rate limit and the hash slots hold it back.
- **Global budget:** all booked tries together, from any mix of callers, are limited to 30 in 10 minutes. Once they are spent every caller gets 429 with `Retry-After` until the window is over, whatever address it comes from, so a flood of source addresses cannot guess faster than that (Skakel does the same for a client's wrong secrets). A right password gives its try back. The cost is that someone who keeps failing from enough addresses keeps the administrator out too; a locked-out administrator uses the reset command below.
- **Table of callers:** at most 2048 entries. When it is full the callers not seen for 2 hours go first, then the unlocked ones not seen for longest. A locked caller is never evicted, so a flood of addresses cannot free one; if every place is held by a locked caller, a new one is not tracked and only the global budget holds it.
- **Hash slots:** at most 2 password hashes run at once for the whole server (setup, login and password change). A caller who arrives while both are busy gets 429 with `Retry-After: 1` at once, and the try is not counted against it. A caller that is locked, or any caller while the global budget is spent, is told so before a slot is taken, so a few locked addresses cannot keep both slots busy and give the administrator a 429.
- **Failures in the log:** every failure goes to the log. The activity log gets one `signInFailed` entry each time a lock engages, so a burst of guesses cannot push the 500 other entries out.
- **Sessions:** they are kept in memory, in a table from id to session (the 12 hour expiry, the 7 day cap, and a `CancellationToken`), at most 256 of them: past that the one that would end first goes. Nothing about a session is written to disk, so **a restart signs everyone out**, and there is no key file, no security stamp and no list of signed-out sessions. Expired sessions are dropped once a minute. Signing out removes one session, so a copy of its cookie is refused. A password change ends every session but the one that made it. A reset or a hand edit of `ui-auth.json` while Koppel runs (the file's watcher sees a password this server did not write) ends every session. Ending a session cancels its token, which closes that session's live push at once; a push stream also ends when its session runs out. In the browser the sign-in gate (`AuthGate`) shows the login screen on any 401, and re-asks the server whether the session is still good when the push stream closes and on every reconnect retry, so a session that ended during an outage does not retry forever. Signing out cancels any auth check in flight and ignores rechecks until it finishes, and a failed sign-out says so.
- **On disk:** `ui-auth.json` holds the password hash only. A file an older version wrote may still carry a security stamp and a list of signed-out sessions; they are ignored and go the next time the password changes. `keys/ui-session.key`, which 0.2.0 signed its cookies with, is deleted at the first start of this version (the log says so).
- **Where the rule lives:** `api::router` in `koppel-web/src/api/mod.rs`. Every `/api/v1/*` route of the UI surface, the live push included, is in the protected group behind `require_session`, and so is a path no route has (401 signed out, 404 signed in); only the anonymous group is open: `/api/v1/auth/state`, `/api/v1/auth/setup` and `/api/v1/auth/login`, besides `/healthz` and the SPA files. Paths are matched as written, so `/API/settings` is not an API path: it is the UI's page, which holds no data. The network surface never looks at the cookie; it keeps bearer tokens.
- **Forgot the password:** run the reset command. It clears the password (so every session of a running Koppel ends) and exits. A running service sees the change through its file watcher and opens the setup window again at once; otherwise the next start opens it. Then set a new password in the UI within the window. An unreadable `ui-auth.json` is replaced by the reset.

  ```sh
  docker compose exec koppel koppel reset-password   # or: docker compose run --rm koppel reset-password, if it is not running
  sudo koppel reset-password                        # Linux package
  ```

  ```powershell
  # elevated prompt
  & "C:\Program Files\Matumi\Koppel\Koppel.exe" reset-password
  ```

### Keeping the key outside the volume

The files are sealed with AES-256-GCM. The key can come from a file kept apart from the config and keys directories, so a backup or a copy of the volume does not carry it. The first of these that applies is used:

1. **`KOPPEL_KEY_FILE`**: the path of a file. When it is set the file must exist, otherwise Koppel stops and says so.
2. **A systemd credential** named `koppel-key`: `LoadCredential=koppel-key:/etc/koppel/key` (or `ImportCredential=`) in the unit makes `$CREDENTIALS_DIRECTORY/koppel-key`, readable by the service only and not by the other users on the machine. The `.deb`'s unit (`koppel.service`) has this line ready, commented out; uncomment it once `/etc/koppel/key` exists, since with the line on the service does not start without the file.
3. **A Docker secret** named `koppel-key`: mounted at `/run/secrets/koppel-key`. In Compose, list it under `secrets:` for the service and under the top level `secrets:` as a `file:` or `external` secret. `docker-compose.yml` has both parts ready, commented out, for a secret from the file `./koppel-key`. The Windows compose files are Windows containers, which keep DPAPI, so they have none.

The file is any secret of 32 bytes or more, up to 4096; a trailing line break is ignored. Make one with:

```sh
openssl rand -base64 32 > koppel-key
chmod 600 koppel-key
```

The AES key and a key id are derived from it with HKDF-SHA256, so the same file is the same key every time. Windows ignores all of this and keeps DPAPI (Koppel warns if `KOPPEL_KEY_FILE` is set there).

Moving an install over: set the source and start Koppel. The old `koppel-secrets.key` in the keys directory is then only read, never made again, and at start every secret file sealed with it is written again with the new key (the log says how many). Once the log says so, stop Koppel, move `koppel-secrets.key` out of the keys directory (keep a copy with your offline backup, not in the volume), and start again. Losing the key outside the volume makes the secret files unreadable, as losing the keys directory does: see "If the key ring is lost" in `docs/config.md`. Back the key up separately from the volume.

Rotating the key, with the key in the keys directory: stop Koppel, rename `koppel-secrets.key` to `koppel-secrets.<anything>.key`, start Koppel. It makes a new `koppel-secrets.key`, reads the renamed one, and seals every file again with the new key. When the log says so, delete the renamed file. Rotating a key from outside the volume is the same with a new key file: copy the old key file into the keys directory as `koppel-secrets.<anything>.key` (a retired key may be a Koppel key file or a plain secret like the ones above), point the source at the new one, start Koppel, and delete the copy once the log says the files were sealed again.

What this buys: a copy of the volume alone, such as a backup, a snapshot or a disk image of the data folder, no longer opens `secrets.json`, `connection.json` and `ui-auth.json`. What it does not: a copy of the machine's whole file system, or root on the running machine, still has the key.

### Guards on the web surface

Each guard is a layer on the router that needs it (`koppel-web/src/guard.rs`, placed in `routes.rs` and
`api/mod.rs`), so a new route is safe by construction. Outermost first, the UI router has the security
headers, a panic catcher, a request trace at debug level, the refusal of a request with no caller address,
a 30 second timeout and a 10 second body-read timeout, the 404 for a path of the network surface, and `Ui:AllowFrom`; its `/api` adds the
origin check, the session reader and `Cache-Control: no-store`; each group of routes adds its own role gate, session requirement and
rate limit. The network router has the same headers, panic catcher, trace and address check, and the role
gate (server or both). Every guard has an integration test that calls the routers with
`tower::ServiceExt::oneshot` (`koppel-web/tests/guards.rs`).

- **Caller address:** a request that reaches a router without the caller's address (`ConnectInfo`) is refused with 500 and an error in the log, since `Ui:AllowFrom`, the limits and Skakel's per-address limits all read it and a guess would fail open. The accept loop adds it to every request; the systemd watchdog's in-process `/healthz` probe adds the loopback address.
- **Order:** on the UI port `Ui:AllowFrom` answers first (403 for every UI path, so a caller it turns away learns nothing else), then the origin check (403), then, for a route that has one, the role gate (404 when this machine's role lacks the route, signed in or not), the rate limit (429) and the session (401). 0.1.x checked the role before `Ui:AllowFrom`; now an address the setting turns away sees 403 for a path of the role it lacks where it saw 404. A path of the network surface on the UI router is 404 before `Ui:AllowFrom` looks at it.
- **Origin and header (UI surface):** on any `/api/v1/*` call, the live push included, `Sec-Fetch-Site` decides when the browser sends it: `same-origin` and `none` (the person's own navigation) pass, anything else gets 403, whatever the `Origin` says. For a browser or proxy that sends none, the `Origin`, when there is one, must be https and have this request's own host and port (compared as `http::uri::Authority`, the host in any case), otherwise 403. `X-Forwarded-Proto` is not read. A change (anything but GET or HEAD) also needs `X-Koppel-UI: 1`, otherwise 403. A page on another site cannot add that header without a CORS preflight, which this server never grants. The UI adds it in `api/http.ts` (`uiFetch`, used by every mutating fetch). The live push is a GET, so it needs no header, which an `EventSource` cannot send.
- **Host header:** the `Host` header is not checked. A DNS rebinding page is stopped by HTTPS: the browser checks Koppel's certificate against the rebinding page's own host name and the request fails, and a page that tries plain HTTP is only redirected to HTTPS at its own host name, where the same check fails. The SameSite=Strict cookie and the Origin and header checks stand behind that, not the host name.
- **Connections and timeouts:** each listener serves at most 512 connections at once (below the 1024 open files a service often starts with, and far more than one admin and a few clients use). The accept loop takes a place before it accepts, so the connections past the cap wait in the system's backlog, not in tasks and memory, and it logs a warning when the cap is reached; a stop still stops with every place taken. A connection that has not sent a byte, or has not finished the TLS handshake, in 10 seconds is dropped. On the UI router (tower-http), a handler that has not answered in 30 seconds gets 408 and a request body that goes 10 seconds without another piece is given up on (the JSON extractor answers 400), so a sender that trickles bytes cannot hold a connection; the body limit is axum's 2 MiB. The network router has neither: gRPC calls and USB streams are long and quiet between messages. Skakel bounds its own calls there (30 seconds for an HTTP/1.1 request's headers, HTTP/2 keep-alive, 4 KiB bodies on its token and pairing calls).
- **Stopping:** when the server stops, every request carries a token that is cancelled, and the live push ends on it, so a stop with a UI tab open takes no longer than one without (it used to wait out the 3 second grace period for the stream). A connection still shaking hands is dropped. Other connections get the 3 second grace to finish, then are aborted.
- **Caching:** every answer under `/api`, refusals included, carries `Cache-Control: no-store`, so the client secrets, the settings and the session state stay out of browser and proxy caches. The UI's files keep their own caching.
- **Security headers** on every response: `X-Frame-Options: DENY`, a `Content-Security-Policy` that allows the page's own origin only (`default-src 'self'`; scripts, fonts, images and `connect-src` for the live push and the API are `'self'`; no objects, no `<base>`, no framing). Styles also allow inline, because react-aria adds `<style>` elements at run time; scripts never do, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- **Rate limits:** a fixed one-minute window per caller, answering 429. A caller is one whole address, an IPv4-mapped IPv6 address counting as its IPv4 address. Skakel limits its token endpoint to 60 (`KOPPEL_RATE_TOKEN_PER_MINUTE`) and its pairing endpoints to 120 (`KOPPEL_RATE_PAIR_PER_MINUTE`), and refuses a body over 4 KiB on them with 413. It also answers 429 to a registered client's token requests after 10 wrong secrets in a minute, from any mix of addresses. Koppel limits `/api/v1/auth/setup`, `/login` and `/password` to 30 (`KOPPEL_RATE_AUTH_PER_MINUTE`), counted the same way, by whole address. The windows that are over are dropped once a minute, and the table holds at most 4096 callers: past that the caller whose window began first is forgotten, so a flood of addresses cannot grow it. Nothing else has a rate limit: `/api/remote/*`, the remote hub and the streams need a valid token. Skakel sits behind the port and role check, as Koppel's own limit does, so a token or pairing request that reached the wrong port or a client-only machine gets 404 without using up an allowance (see "Limits" in ["The roles on Skakel in Rust"](skakel.md#the-roles-on-skakel-in-rust)).
- **Remote hub:** Skakel closes a connection when its token runs out, and the link makes it again 30 seconds before that, with a fresh token. Koppel shows nothing of it: no "connecting" and no entry in the activity log.
- **Connection test:** the client's Test button gets one of a fixed set of outcomes with fixed wording, never raw exception text: `ok`, `incomplete`, `unreachable`, `certificateMismatch`, `rejectedCredentials`, `clientUnknown`, `versionMismatch` (Skakel's wording, which names both sides' protocol versions), `unexpectedAnswer` and `tooManyRequests`. They are Skakel's failure kinds, mapped in `tested` in `koppel-app/src/roles/skakel/client.rs`; a revoked or rotated client reads as `clientUnknown`. `unexpectedAnswer` also covers an answer over Skakel's 64 KB cap, and `tooManyRequests` a client that had too many wrong secrets in the last minute. The detail goes to the log.
- **Dev proxy:** the Vite dev server proxies `/api` to `KOPPEL_UI_URL`, default `https://127.0.0.1:5240`, the UI port, without verifying Koppel's self-signed certificate. The Origin check no longer reads `X-Forwarded-Proto`: the browser's `Sec-Fetch-Site` passes through the proxy, and the origin's host and port match the host the proxy forwards.

### Threat model

What the design holds against:

- A stranger on the network reaching the UI: the UI needs a password, and guessing it is slowed by the backoff. Before the first password is set, though, whoever reaches the UI first during the setup window can set it and so claim the machine. `KOPPEL_UI_ALLOW_FROM` limits who that can be: the local network by default, this machine only on a native Windows install. On Linux and in Docker, when it is not `local`, they also need the one-time setup token from Koppel's log, so a neighbour who cannot read the log cannot claim the machine; native Windows has no token. The window closes after 10 minutes (`KOPPEL_UI_SETUP_WINDOW_MINUTES`), so a machine left without a password does not wait for anyone who comes along; a restart opens it again. Set the password as soon as Koppel first starts, and on a network you do not trust, start it with `KOPPEL_UI_ALLOW_FROM=local` until you have. Behind Docker Desktop every caller looks like the same address, so `KOPPEL_UI_ALLOW_FROM` cannot narrow it there (see `docs/windows.md`).
- A web page in the admin's browser calling the UI: SameSite=Strict, the Origin check and the `X-Koppel-UI` header.
- A stranger reaching the network surface: it is only Skakel's info, token and pairing endpoints, which have rate limits, and the remote API, the remote hub and the USB stream, which need a token from a client registered at its current generation. The UI on the same port turns away callers outside `KOPPEL_UI_ALLOW_FROM` (the local network by default) and needs the password. Plain HTTP on the port gets only a fixed redirect, before TLS.
- A stranger sending discovery packets: a server answers only a full-size probe, never with more bytes than the probe had, and a malformed or oversized datagram is dropped without stopping the answers. A probe from port 0 or from an address that is not one host (unspecified, broadcast, multicast) gets no answer, and an answer that cannot be sent is logged at debug and does not stop the next one. A client keeps a bounded list of answers (Skakel's discovery limits), and a server it hears is trusted only through its pinned certificate and the pairing code.
- A man in the middle during pairing: Skakel derives the eight-digit code from the pinned certificate, the client's name and both nonces, with a commitment, so it gets one guess in a hundred million per request, and the server limits the requests and takes them only while a person has opened the pairing window. Only the opener of a request holds its poll token, so nobody else can collect the credentials.
- A revoked client: its sessions end and it cannot get a new token.

What it does not cover:

- The browser cannot tell Koppel's self-signed certificate from an attacker's. It warns the first time, and whoever accepts the warning on a network they do not trust can be shown an impostor that collects the password. The certificate's SHA-256 fingerprint is the one under Clients, so it can be checked in the browser's certificate details. On Windows the installer sets `KOPPEL_UI_ALLOW_FROM=local`, so the UI answers this machine only; the port itself listens on every address, because other Koppel machines use it. The Docker Desktop compose file for a Windows client publishes the port on `127.0.0.1`; the one for a Windows server publishes it on every address, as a server must.
- `KOPPEL_UI_ALLOW_FROM` and the per-caller limits on sign-in and pairing go by the caller's address as Koppel sees it; forwarded headers are not read. Behind NAT, such as port publishing that rewrites the source address, every caller arrives from one address: the local network check then lets everyone in, and one caller's wrong passwords lock out everyone else's address too.
- The gateway on 3242 is plain USB/IP with no login (see ["USB client"](usb.md#usb-client)). Whoever reaches it uses the client's access to the server. On native Windows with a loopback address only the kernel's own connections get in, and only for imports Koppel asked the driver for; elsewhere, such as a container, the port publishing is all that keeps it local.
- A registered client and the server it is paired with trust each other's USB/IP traffic: what one sends goes to the other's kernel driver (`usbip-host`, `vhci_hcd` or usbip-win2's driver) as it comes, and an attached device can be any device, a keyboard that types included. Koppel checks the bus ID and VID:PID of an import, not the traffic after it.
- **On Linux and in Docker the key sits beside the files it protects.** By default `koppel-secrets.key` is in the keys directory, and the keys and config directories are one volume (`/koppel` in the image). A backup or a copy of the volume holds the key and the ciphertext together, so the encryption then protects only a copy of the config directory on its own. Anyone who can read the keys directory can decrypt the secret files. Keep the key elsewhere to change that (see "Keeping the key outside the volume" below). On Windows the key is machine-scope DPAPI: any process on the machine can unseal the files, as with 0.1.x.
- **The key is not a passphrase.** Koppel has to start unattended after a power cut, so nothing asks for one at start. A key kept outside the volume is still a file that Koppel reads at start, and root on the machine can read that file, or the process's memory, as it can for any service.
- **Memory.** Secrets are decrypted into memory while Koppel runs: the certificate's private key, client secrets, the UI password hash. The values Koppel owns are wiped when they are dropped (`Secret`, and the buffers holding a decrypted file). That is best effort: the JSON parser's intermediate copies, the TLS stack's keys and the AES key schedule are not wiped, nothing is locked out of swap, and a core dump holds them. Turn core dumps off on a machine that matters (`LimitCORE=0` in the service, `--ulimit core=0` in Docker).
- **Logs.** The config structs print `Secret(<redacted>)` for every secret, so a `{:?}` of one cannot leak it. A test holds that line. Koppel's own log messages do not carry secrets; a log line written by hand that formats a secret is the way one gets out, and the `Secret` type has no `Display` to make that easy.
- **The 0.1.x key ring stays.** After a 0.1.x install is converted, its Data Protection key ring (`key-*.xml` in the keys directory, with the master key in plain base64 on Linux) is left where it was, and Koppel never deletes it. Until you delete it, it can decrypt whatever 0.1.x sealed, including a backup of the old files. Back up the data folder, then delete the `key-*.xml` files by hand; there is no command. See "The 0.1.x key ring is kept" in `docs/config.md`.
- **Client secrets can be read again.** Koppel keeps each client's secret inside the encrypted `secrets.json` so the admin can copy it again from the client's row. Anyone who can read the decrypted file can read them; see "Client secrets stay retrievable" in `docs/decisions.md`.
- The Linux container is privileged and runs as root, and the Windows service runs as LocalSystem. A flaw in Koppel is a flaw with that reach. On Windows the reach is cut in one respect: the installer limits the service's token to eight privileges (see "The service keeps eight privileges" in `decisions.md`), where LocalSystem starts with about thirty, so a flaw does not come with the right to debug any process, load a driver, read any file regardless of its ACL or shut the machine down. The installer's `PrepareDataFolder` step runs as SYSTEM in the installer, not under that limit, and `Koppel.exe prepare-data-folder` (its code is shared with the service's own start-up hardening) is the one place the data folder's ACL is written.
